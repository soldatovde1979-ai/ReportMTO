# Установка правок v6

Пакет собран поверх v5. Всё, что было в v5, входит сюда целиком — ставить v5 отдельно
не нужно, если он ещё не поставлен. Если v5 уже стоит, меняются только файлы из таблицы ниже.

## Что изменилось против v5

| Файл | Статус |
|---|---|
| `src/powerquery/fnComputeKey.pq` | изменён — **`status_date` включён в ключ** (K-2) |
| `src/vba/modContentMTO.bas` | изменён — HTML-сущности вместо `Δ`/`∈`/`↔`, единое сравнение статуса |
| `tests/ОЖИДАЕМОЕ_v2.md` | заменяет `ОЖИДАЕМОЕ_v1.md` — эталон под новый ключ |
| остальные файлы v5 | без изменений |

В комментариях всех `.bas` спецсимволы заменены на ASCII (`->`, `x`, `(!)`). Причина —
сборочный скрипт конвертирует исходники в кодировку системы перед импортом в VBA, и
символы вне Windows-1251 превращаются в `?`. В `.pq` и `.ps1` это не требовалось: первые
уходят в COM строкой, второй читается как UTF-8 благодаря BOM.

## Порядок

**Шаг 0. Разово выключить уровни конфиденциальности.** Excel -> Данные -> Получить данные
-> Параметры запроса -> Глобальные -> Конфиденциальность -> «Всегда пропускать параметры
уровня конфиденциальности». Без этого Formula Firewall отклонит обновление независимо от
кода. Настройка глобальная, задаётся один раз. Если v5 уже ставился — шаг сделан.

**Шаг 1.** Скопировать файлы поверх одноимённых в репозитории.

**Шаг 2.** `prmSourcePath`: либо ничего не делать (первое нажатие «Загрузить» перезапишет
его вместе с meta-записью параметра), либо удалить в панели «Запросы и подключения» до
сборки, тогда скрипт создаст его сразу параметром.

**Шаг 3.** Сборка:

```powershell
.\tools_Build-ReportMTO.ps1 -ProjectRoot "C:\путь\к\ВашаПапкаПроекта"
```

**Шаг 4.** Открыть `qExistingData` -> Закрыть и загрузить в... -> **Только создать
подключение**. На лист не грузить.

**Шаг 5.** Alt+F11 -> Debug -> Compile VBAProject. Должно пройти молча.

**Шаг 6. ОЧИСТИТЬ `tbDATA`, оставив строку заголовков.** Обязательно и только один раз.
Формат ключа изменился, поэтому старые строки не совпадут с новыми ни по одному ключу:
они не заместятся, а лягут рядом, и таблица удвоится. Проверено на модели: 25 строк
превращаются в 50.

**Шаг 7.** Загрузить `tests/test_sppr_tablet_v1.json`, сверить с `tests/ОЖИДАЕМОЕ_v2.md`.

**Шаг 8.** Только после совпадения — реальная выгрузка.

## Что даёт правка ключа и чего она стоит

Ключ стал `number | date | ready_for | direction | status_date` — идентифицирует событие,
а не пару «наряд + статус».

Закрыто: два события одного наряда с одним статусом больше не делят ключ. В v5 при
частичной выгрузке одна из строк молча исчезала, а `deltaHours` пересчитывался по
оставшейся — на `ЗН-006` это давало 20 ч -> 16 ч без единого сообщения.

Цена: если 1С скорректирует `status_date` уже выгруженного события, строка со старым
временем не совпадёт по ключу и останется рядом с новой. Замена работает только при
полном совпадении всех пяти полей. Обратная сторона — события с одинаковыми пятью полями
теперь означают дефект выгрузки, и это видно проверкой на дубли `Key`.

## Осталось нерешённым (не входит в v6)

`deltaHours` считается в `fnComputeGroupMetrics` ДО слияния, то есть в пределах одного
файла. Наряд, у которого приёмка пришла в одной выгрузке, а выбытие в следующей, дельты
не получит. Пока 1С отдаёт полную историю каждый раз — не проявляется. Если перейдёте на
инкрементальные выгрузки, метрику придётся считать после upsert, а это уже изменение
порядка шагов в `Query-ImportJSON` и отдельная задача.
