## 1. Паспорт

**Что это:** система отчётности по ремонту техники МТО (MTO Smart Analytics). Вход — JSON-выгрузки из 1С (`data/sppr_tablet_*.json`), обработка в Power Query + VBA внутри книги Excel `ReportMTO.xlsm`, выход — HTML-отчёт на 8 слайдов в `result\`, с опциональным вызовом внешнего ИИ (DeepSeek) для текстовых выводов.

**Для кого:** руководитель/инженер по технике, принимающий решения по парку техники по недельному отчёту.

**Стек:** Excel (книга .xlsm) · VBA (11 модулей, ~13,7 тыс. строк) · Power Query M (18 запросов) · 1С-запрос на выгрузку (`src/1C/export2mto.bsl`) · PowerShell (сборка, установка, запуск отчёта) · Python/утилиты в `tools\`.

**Точки входа:**
- `run.bat` → `tools\run_report.ps1` — двойной щелчок: открыть книгу, построить сводные и отчёт.
- Книга: кнопки «Загрузить» (`modMain.LoadSourceFile`) и «Загрузить пакет» (`modMain.LoadPackage`), «Сформировать» (`modMain.GenerateReport`).
- `install\install.ps1` / `install\release.ps1` — раскатка версии; `tools\build-report-mto.ps1` — сборка книги из `src\`.

**Что проверено и чем:**
- Прочитаны: README, AGENTS, docs\tasks.md, docs\spec.md (разделы), CHANGELOG, VERSION, run.bat, все модули `src\vba\` целиком (modMain, modAIGateway, modHTMLEngine, modLog, modPQSync, modColor) или структурно (modContentMTO — карта функций, sig-файл), PQ-конвейер (Query-ImportJSON, fnComputeKey, fnDedupByKey, fnComputeGroupMetrics), `tools\run_report.ps1`, `tests\modSelfTest.bas` (шапка), .gitignore.
- Запущено: скрипт профиля `data\` (чтение JSON, агрегаты без персональных значений), grep-сканы секретов, подсчёт плейсхолдеров шаблона.
- Профиль `data\`: 4 файла JSON, суммарно 142 124 записи, 28 полей. Одна строка = событие смены статуса ЗН (наряд). Ключ на пару (number, direction) не уникален по построению — статусная история (~4 события на ЗН). Диапазон sample-файла: 2026-09-01…2026-09-10. Пропуски: status_date пуст у 32%, odometer — 59% null, engine_hours — 40% null, defekt_type/defect_desc — ~10% null; model_type вырожден (1 значение). Файлы перекрываются по содержимому (полные снапшоты) — конвейер обязан дедуплицировать, что и делает.
- ⚠️ Предположение: пользователь отчёта — руководитель, принимающий решения по парку; из README/spec явно не следует, какое решение принимается по отчёту.

## 2. Плюсы решения

- **Явная архитектура Core/Content Spec** с контрактами по фиксированным именам — Core (`modMain`, `modPQSync`, `modAIGateway`, `modHTMLEngine`) не знает специфики МТО; расширение под другой отчёт — только Content-модули (`docs\spec.md` §2, шапки модулей).
- **Документация исключительного для такого размера проекта качества:** README-карта, `docs\spec.md`, `docs\data.md`, sig-файлы на каждый модуль (`src\sig\`), `docs\version-guide.md`. История решений владельца записана в комментариях к коду (fnComputeKey.pq: K-3).
- **Ключ ИИ вне книги** и не пишется в лог/HTML: env `AI_API_KEY` → `%APPDATA%\ReportMTO\deepseek.key` → legacy Variable с предупреждением (`modMain.ResolveAiApiKey`); диагностика — источник/длина/префикс без раскрытия секрета.
- **UTF-8 дисциплина сквозная:** BOM отсекается и при чтении ключа, и при записи отчёта (`modHTMLEngine.ReadUtf8/WriteUtf8`), тело запроса к ИИ уходит байтами UTF-8 (`modAIGateway.TextToUtf8Bytes`) — класс «кириллица ломается» закрыт системно.
- **Экранирование HTML** платформенной функцией на всех подстановках (`modHTMLEngine.HtmlEscape`).
- **Деградация вместо падения:** недоступность ИИ-слоя не блокирует отчёт (`modMain.GenerateReport`, блок «Внешний ИИ»); недоступная папка результата — фолбэк на `result\` рядом с книгой с записью в журнал (`modHTMLEngine.SaveHTMLFile`).
- **Идемпотентная сборка книги** с продолжением с места падения (`tools\build-report-mto.ps1`).
- **Тесты есть и смысловые:** `tests\modSelfTest.bas` + `run-e2e-tests-v1.ps1` + фикстуры + эталоны `tests\expected.md`, проверка upsert на повторных ключах.
- **run_report.ps1 сделан аккуратно:** собственный COM-инстанс (не GetActiveObject), проверка lock-файла, контроль появления свежего `Report_*.html`, Close без сохранения в finally.
- **Дедупликация и retention продуманы:** правило победителя задокументировано с ценой на примере (`fnDedupByKey.pq`), рост tbDATA ограничен ретеншном по неделям (`Query-ImportJSON.pq`, шаг R-1).
- **Пакетная загрузка ускорена с 5 ч 12 мин до минут** — upsert заменён однопроходной пересборкой (`Query-ImportJSON.pq`, v7.4/R-2; замеры в `docs\tasks.md`).

## 3. Минусы и слабые места решения

- **Монолиты Content Spec:** `modContentZone.bas` — 5839 строк, `modContentMTO.bas` — 4385 строк. Один модуль держит и расчёты, и HTML-разметку, и сборку промпта. Правка одного слайда требует работы с файлом на тысячи строк.
- **Дубликат конвейера:** `src\powerquery\qProf1_Source.pq … qProf7_Retention.pq` — 7 × 203 строки, пофайловая копия цепочки `Query-ImportJSON` для профилирования (задача A, `docs\tasks.md`). Профиль снят и зафиксирован — копии потеряли актуальность как документация, но продолжают выглядеть второй реализацией.
- **Шаблон с именем «tmp_»**: постоянный рабочий артефакт `tmp_index.html` (150 КБ, 81 плейсхолдер) ищется по хардкоду `ThisWorkbook.Path & "\tmp_index.html"` (`modMain.GenerateReport`). Имя подталкивает к удалению, а перенос книги без шаблона даёт ошибку чтения файла без внятного текста.
- **Мусор в корне и build\:** пустой файл `NOT` (0 байт); `build\ReportMTO v7.0.xlsm.bak_20260908_144806` и `build\tmp_index.html.bak_…` — нарушение собственного правила README:41 «бэкапы — только в `bak\`»; ~10 диагностических `*_tmp*` скриптов в `tools\` (diag_*_tmp.ps1, load_prod_tmp.ps1 и др.), которые по тому же правилу подлежали удалению после использования.
- **Старые построители блоков 1–9** остаются в `modContentMTO` и не вызываются из `BuildPlaceholders` (sig: «постановка §8 — не удалять»). Решение осознанное, но ~40% монолита — неактивный код, который IDE-компиляция не отличит от живого.
- **Логирование O(n²) по объёму журнала:** каждое сообщение перечитывает весь `ReportMTO.log` и перезаписывает файл целиком (`modLog.AppendToFile`: LoadFromFile → SaveToFile overwrite). При DEBUG=2 и лимите записи 100 000 символов каждая строка лога стоит всё дороже.
- **`GetDebugLevel` вызывается на каждую запись** (`modLog.WriteDebug` → `GetDebugLevel` → `AppendToFile` → `GetDebugLevel`), а чтение — линейный перебор листа Variable (`modMain.GetVariable`). На длинных прогонах это заметная доля времени.

## 5. Замечания по коду

**Корректность**
- `modMain.ClearTbData` — тело после `Exit Sub` недостижимо, функция ничего не делает (заглушенная история про зависание на 255 тыс. строк). Читатель ожидает очистку, которой нет. Фикс: переименовать в `ClearTbDataNoop` или удалить вместе с вызовом.
- `modMain.LoadPackage`: прогноз «~N мин» строится от прошлого прогона по линейной экстраполяции (`lastSecs/lastRows*totalRecs`) — при добавлении файлов другой размерности прогноз уводит; это осознанно (первый замер подписан), но стоит подписывать «прогноз по прошлому прогона» прямо в строке статуса.
- `Query-ImportJSON` SampleFields берёт поля из первых 1000 записей — поле, впервые встреченное позже, молча не попадёт в таблицу (задокументировано в коде, есть `qDiagImport`). Для боевых выгрузок одной схемы риск низкий, но после смены схемы 1С проявится именно так.
- `modMain.LoadPackage`: `estMins = (lastSecs/lastRows*totalRecs)/60` — `lastRows`/`totalRecs` не защищены от нуля выше по ветке для `totalRecs = 0` (все имена не распознаны) — деление даст inf-подобную строку в статусе. Фикс: `If totalRecs > 0`.

**Обработка ошибок**
- `modMain.bas` — 7 × `On Error Resume Next`; большинство оправданы (резолвер ключа, чтение ключа файла), но в `SafeRowCount` ошибка листа неотличима от «0 строк» — отчёт в этом случае корректно скажет «tbDATA пуста», а не «нет листа». Приемлемо, но при рефакторинге листов проверку стоит вынести.
- `modLog.AppendToFile` молча глушит все файловые ошибки (`Done:` без записи) — задокументировано как «файл — зеркало листа». При заблокированном антивирусом файле лог молча не ведётся, а лист Logs при DEBUG>0 тоже пуст для «Инфо»-типов. Сценарий «всё сломалось, а журнала нет» возможен. Фикс: разово писать `Debug.Print` при неудаче создания файла.

**Читаемость**
- Дубли парсинга `rec.`-счётчика: `RecFromName` и `SumRecsFromNames` (`modMain.bas:279–324`) — одна логика дважды, комментарий честно это признаёт. Фикс: `SumRecsFromNames` переиспользует `RecFromName`.
- `modMain.ListJsonFiles` — пузырьковая сортировка; для типовых 5–10 файлов неважно, замечание носит справочный характер.

**Производительность**
- `modLog.AppendToFile` — O(размер файла) на каждую запись (см. риски). На DEBUG=2 с сотнями записей это секунды-минуты чистых потерь. Фикс: держать поток открытым на сессию или писать через FSO append.
- `modMain.GetVariable` — линейный перебор строк на каждый вызов; в горячих местах (логирование) кэшировать словарь при первом чтении. Соразмерно: лист Variable — десятки строк, проблема только в сочетании с двумя пунктами выше.

**Производительность — что уже хорошо:** `BuildPivots` на 137 тыс. строк — 1,5 c (лог от 16.09.2026); узкое место загрузки устранено (R-2); `fnComputeGroupMetrics` переписан одним проходом (v8.3).

## 6. Интерфейс (run.bat → отчёт)

- **Понятно, что происходит:** run.bat сообщает этапы и честно предупреждает «это может занять несколько минут»; run_report.ps1 ставит метки `RUN_START/RUN_OK/RUN_FAIL/RESULT_FILE` — легко диагностировать по тексту.
- **Ошибка в run.bat — «подробности выше в окне»** — корректно, потому что окно держится `pause`.
- **GenerateReport пишет прогресс в StatusBar книги** («Ожидание ответа внешнего ИИ…»), но при `Visible=$true` пользователь может этого не заметить; кнопка не блокируется от двойного запуска — повторный клик по «Сформировать» во время прогона соберёт второй отчёт. Фикс: показывать немодальное окно/менять текст кнопки на время прогона.
- **Хрупкость шаблона:** для пользователя нет диагностики «не найден tmp_index.html» — только системная ошибка чтения файла. Фикс: в `modMain.GenerateReport` перед RenderTemplate проверять `Dir(templatePath)` и писать понятную ошибку («шаблон не найден рядом с книгой»).
- Итог: интерфейс для одного оператора-владельца достаточен; узкие места — диагностика шаблона и защита от повторного запуска.

## 7. Аналитика и данные

**Качество данных (профиль из §1):**
- `status_date` пуст у 32% записей — это осознано и обработано (опорная дата = max(status_date, date), `Query-ImportJSON.RowAnchor`).
- `odometer` (59% null) и `engine_hours` (40% null) — годятся только как вторичные признаки; в spec.md §9 это уже зафиксировано.
- `model_type` вырожден (1 значение в sample) — как измерение бесполезен, разрезы по нему пустые.
- Ключи: 2488 из 2488 пар (number, direction) имеют несколько строк — это статусная история, конвейер её корректно дедуплицирует по Key и сворачивает в deltaHours.
- Файлы выгрузки перекрываются (полные снапшоты планшета) — без дедупа tbDATA рос бы квадратично; dедup по Key с правилом «max status_date» семантически корректен.

**Корректность расчётов:**
- `deltaHours` = tEnd − tStart по статусам «готов к приёмке»/«готов к выбытию»; правило при дубликатах задано явно (fnDedupByKey.pq, пример с ценой изменения — в шапке функции). Хорошая практика.
- Ограничение по построению: «синхронность дирекций» в документе одна дата на обе дирекции — неизмеримо (spec.md §9); отчёт это не может показать, и хорошо, что не показывает.
- Риск искажения: медианы по видам при малых выборках (zn_type с долей < 3%) могут качаться от недели к неделе — если такие разрезы показываются, нужна минимальная численность группы.

**Что может ввести в заблуждение:** выводы ИИ (слайды) строятся по агрегатам без ФИО и defect_desc (BuildPrompt по белому списку) — но читатель не отличит текст ИИ от расчётного текста; подпись «выводы сформированы ИИ» в шаблоне стоит сделать заметнее (шаблон не проверялся построчно — см. §10).

**Не хватает данных:**
- Норматив длительности/стоимости по виду ремонта (справочник «zn_type → норма-часы/бюджет») — без него все отчёты по deltaHours и затратам описательные, «% от нормы» посчитать не из чего.

- Дата статуса документа (упомянута в постановке v2.7 — «в выгрузке нет») — блокирует честные разрезы «сколько времени висит в текущем статусе».
