## 4. Инструменты сборки/разработки (НОВОЕ, добавлено 24.08.2026)

По запросу пользователя проведена ревизия инструментов для разработки в VS Code и
автоматической сборки книги:

- **VS Code ↔ Excel:**
  - `ewc3labs.excel-power-query-editor` — извлекает M-код в `.m`-файлы, режим
    «Intelligent Auto-Watch» пишет изменения прямо в `.xlsm`/`.xlsb` без открытого Excel.
    Рекомендован для `src/powerquery/*.pq`.
  - `markuskiller/vba-edit` (PyPI CLI, xlwings/COM) — режим watch пишет изменения `.bas`
    в ОТКРЫТУЮ книгу Excel по сохранению файла. Рекомендован для `src/vba/*.bas`.
  - `PowerQuery.vscode-powerquery` (официальный MS) — только подсветка/статический
    анализ M, без синхронизации; можно держать вместе с ewc3labs как language server.
  - VBA-подсветки (serkonda7/spences10/skyran) — чисто косметические, не заменяют vba-edit.
- **Автосборка:** `tools/Build-ReportMTO.ps1` — PowerShell + COM-автоматизация Excel:
  1) заготовка → `.xlsm`, 2) импорт всех `.bas` (`VBComponents.Import`, задокументированный
  API), 3) создание 6 Power Query-запросов (`Workbook.Queries.Add`, задокументированный API,
  порядок: `prmSourcePath` → 4 функции → `Query-ImportJSON`), 4) ⚠️ ЭКСПЕРИМЕНТАЛЬНАЯ попытка
  автоматического «Close & Load To → Table» через недокументированную строку подключения
  OLEDB;Provider=Microsoft.Mashup.OleDb.1 — обёрнута в try/catch, при неудаче не портит уже
  сделанные шаги 1–3, шаг делается вручную. Требует включённого «Доверять доступ к объектной
  модели проектов VBA». Не прогонялся на реальном Excel самим автором скрипта — первый прогон
  должен быть на копии проекта.
- [x] Прогнан `tools/Build-ReportMTO.ps1` на реальном Windows+Excel пользователем — найдены и
      исправлены два реальных бага (см. ниже), скрипт обновлён и переотправлен.
      **Шаг 4 (Load To Table) до реального теста ещё не дошли** — падение произошло раньше,
      на шаге 2 (импорт VBA-модулей); этот пункт остаётся открытым до следующего прогона.
- [x] **Найден и исправлен баг №1**: `$wb.Workbooks.Open($starterXlsx)` падал с
      `COMException` («Невозможно получить свойство Open класса Workbooks»). Причина не
      установлена окончательно (COM-ошибка без диагностического текста), но воспроизводимо
      снималась стандартным чек-листом Excel-automation (PowerShell не «от имени
      администратора», отсутствие зависшего фонового `EXCEL.EXE`, файл не заблокирован
      Windows как «скачанный из интернета» — снять блокировку через Свойства файла).
- [x] **Найден и исправлен баг №2**: импорт VBA-модулей падал на первом же файле
      (`modAggregate.bas`) с `Невозможно вызвать метод для выражения со значением NULL`
      внутри `$wb.VBProject.VBComponents.Import(...)`, при этом более ранняя проверка
      `$wb.VBProject.VBComponents.Count` проходила успешно — т.е. чтение доступно, а запись
      в VBA-проект через тот же объект — нет. Скрипт исправлен: `VBProject` теперь кэшируется
      в переменную один раз сразу после `SaveAs` (плюс `Start-Sleep -Milliseconds 500` перед
      первым обращением к нему), каждый `Import` обёрнут в свой `try/catch` с понятным
      сообщением. Если ошибка повторится и после этого — вероятная причина зафиксирована в
      сообщении скрипта: групповая политика организации может принудительно сбрасывать
      реестровый ключ `AccessVBOM`, даже когда галочка «Доверять доступ к объектной модели
      проектов VBA» в интерфейсе выглядит включённой — это уже вопрос к ИТ-администратору,
      не к скрипту.
- [ ] Дождаться следующего прогона исправленной версии скрипта — подтвердить, что импорт
