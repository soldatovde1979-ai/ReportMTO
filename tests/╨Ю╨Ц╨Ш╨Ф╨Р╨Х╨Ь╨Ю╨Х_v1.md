# Тестовый набор v1 — что должно получиться

Два файла в этой папке. Оба UTF-8 без BOM, как требует конвенция проекта.

- `test_sppr_tablet_v1.json` — 25 событий, покрывают граничные случаи из журнала проекта.
- `test_upsert_same_keys_v1.json` — 2 события с теми же `Key`, но изменённым `arm`.
  Нужен только для проверки замены строк.

⚠️ Ожидаемые значения ниже посчитаны мной на модели пайплайна, а не прогоном Power Query.
Это эталон для сверки, а не доказательство, что M-код работает. Расхождение означает
дефект — либо в коде, либо в моей модели; разбирать по конкретной строке.

## Прогон 1 — загрузка `test_sppr_tablet_v1.json` в пустую `tbDATA`

| Проверка | Ожидание | Что означает провал |
|---|---|---|
| Строк в `tbDATA` | **25** | потеря строк на разворачивании JSON |
| Столбцы `postN`, `yearWeek`, `Key`, `deltaHours` присутствуют | да | не отработал `fnNormalizeFields` / `fnComputeGroupMetrics` |
| Непустых `deltaHours` | **9 строк** | если 0 — снова сравнение статуса не совпадает |
| Ошибок в ячейках (жёлтая полоса «загружено с ошибками») | нет | типизация дат жёстче, чем данные |

Значения `deltaHours` (только у строк «Готов к выбытию»):

```
ЗН-001 ДГМ    5,0      ЗН-004 ДГМ   10,0      ЗН-007 ДЭНТ   3,0
ЗН-001 ДЭНТ   6,5      ЗН-005 ДГМ   10,0      ЗН-010 ДГМ    2,0
ЗН-002 ДГМ   10,0      ЗН-006 ДГМ   20,0
ЗН-003 ДГМ   10,0
```

`ЗН-006` — это проверка допущения min/max: три статусные записи на пару, берётся
самая ранняя приёмка (06:00) и самое позднее выбытие (02:00 следующего дня) = 20 ч.
Если получилось 16 — код взял не min, а последнюю приёмку.

`yearWeek` принимает ровно три значения: **202635, 202535, 101**.
`101` — это строка `ЗН-011` с пустой `status_date`: 1С пишет `year=1, week=1`
(замечание №5 к выгрузке). Она обязана быть видна как отдельный столбец-призрак —
это подтверждение, что замечание к 1С ещё не закрыто, а не ошибка отчёта.

## Прогон 3 — загрузка `test_upsert_same_keys_v1.json`

Строк по-прежнему **25**, но у обеих строк `ЗН-002` поле `arm` стало `ПК`
(было `ПЛАНШЕТ`). Если `arm` остался прежним — upsert работает как anti-join,
то есть новые строки не замещают старые.

## Что должно вылезти как ИЗВЕСТНАЯ проблема, а не как успех

**Дублей `Key` внутри одного файла: 2.** Строки `ЗН-012` — один наряд, одна дирекция,
один статус, две разные `status_date`. Ключ у них одинаковый. При upsert вторая затирает
первую. Это открытый вопрос по составу ключа из аудита, тест его показывает намеренно.

**`postN` схлопывает пять разных постов в «СТК»:**

```
СТК  <-  "СТК, цех 1", "СТК, цех 2", "Стк цех 2", "стк", "Казарма СТК"
ПРК  <-  "ПРК ДГМ", "прк"
```

«Казарма СТК» — отдельная зона в `dictZone`, а нормализация приписывает её к СТК.
Блок 2 показывает `ДГМ / СТК: 6` вместо разбивки по цехам. Это то самое расхождение
между схлопкой и справочником зон, о котором в аудите сказано «решение заказчика».

## Блоки: контрольные цифры под базовым фильтром

Под фильтр (`in_bounds = ИСТИНА`, `arm ∈ {ПК, ПЛАНШЕТ}`) попадают **23 строки из 25**:
отсеиваются `ЗН-008` (`arm = "НЕ ПОДПИСАНО"`) и `ЗН-009` (`in_bounds = false`).

Блок 4, «% планшет» по дирекции × неделе:

```
ДГМ,  нед. 202635 :  10/17 = 58,8 %
ДЭНТ, нед. 202635 :   0/4  =  0,0 %
ДГМ,  нед. 202535 :   0/1  =  0,0 %
ДГМ,  нед. 101    :   0/1  =  0,0 %
```

Блок 2, Distinct Count по `number`:

```
ДГМ  СТК       6      ДЭНТ СТК       1
ДГМ  ПРК       2      ДЭНТ Обмывная  1
ДГМ  Ангар №1  1      ДГМ  (пусто)   1
```

Блоки 7/8: **ровно одна пара** — `ЗН-001`, разница 2,0 ч. `ЗН-007` есть только у ДЭНТ
и в пары не попадает — код обязан его пропустить, а не упасть.
Если таблица пустая («нет пар для сопоставления») — сработал дефект C-1 из аудита,
сравнение `in_bounds` со строкой `"True"`.

Блок 6 при `REPORT/MIN_RECORDS = 5` покажет только **Иванова (8 записей)** и
**Сидорова (8)**; Петров (4) и Кузнецов (3) отсекаются порогом. Это правильное поведение,
а не потеря данных.
