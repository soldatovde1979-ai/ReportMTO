## Ключевые находки (проверены в этой сессии, не по памяти)

| Находка | Почему важно |
|---|---|
| **`status_date` — реквизит документа, не регистр.** Берётся из `т1кДатаПриемки` / `т1кДатаВыдачи`, четырьмя ветками UNION | Это дата подписи. Регистр чекинов используется только для `arm` и `in_bounds`, период отметки не выгружается вовсе |
| **Регистр `eamСтатусыОбъектов` уже в запросе, но берётся только срезом последних** | Вся история смены статусов в 1С ЕСТЬ и отбрасывается. Открывает три «невозможности» разом: реальные фазы наряда, разделение дирекций по времени, честный план/факт |
| **СТАТУС «Готов к приемке» ≠ ПОДПИСЬ приёмки** | Статус = ремзона объявила готовность (люди, место, з/ч). Подпись = инженер ДГМ физически принял и осмотрел. Порядок: создан → статус → подпись планшетом → «В ремонте». Поле `ready_for` — метка подписи, а не состояние объекта |
| **`ПК` означает не «работал за компьютером», а «подпись без подтверждённого присутствия у машины»** | Чекин привязан к пользователю намеренно: подписал один, чекинился другой → ПК, потому что подписант машину не видел. Это суть контроля, а не деталь соединения |
| **Даты ДГМ и ДЭНТ совпадают в 43 333 из 43 333** | Дефект «одно поле на обе дирекции» подтверждён на полном снимке |
| **Метрика «создание → приёмка» смещена по построению** | В неё попадают только наряды с подписью приёмки. Отменённые, не доехавшие до ремонта — те самые, ради которых метрику и смотрят — исключены автоматически |
| **Интервал «приёмка → выбытие» не равен пребыванию техники** | Распределение гладкое, одногорбое, пик 1-4 ч, медиана ~45 мин. Очередь до и ожидание владельца после в него не входят. «Сутки в ремзоне» — не сутки |
| **Файл `...58672rec.json` читается нормально** | В `data.md` он числился битым — снято |

**Аномалии, причина не установлена:** 275 пар с выбытием раньше приёмки; 120 нарядов
с приёмкой раньше создания; `status_date` от декабря 2024 в файле за август-сентябрь 2026.

Копия исходного отчёта, где под каждым блоком врезкой стоит то же мнение. Удобно, когда

### Пять правил, в которые сворачиваются все 65 пунктов «что улучшить»

Это самый переносимый результат разбора — чек-лист, применимый к блоку **до** того,
как он построен:

1. Нормируй на объём — доля, а не абсолют.
2. На хвостатых распределениях медиана врёт, нужен p90.
3. Одна метрика — одно определение на весь документ.
4. У каждого числа должен быть адресат, иначе это украшение.
5. «Год и неделя» — одна картинка двумя сериями, а не два блока.

Плюс рамка, по которой блок либо живёт, либо уезжает в приложение:
**вопрос → метрика → разрез (кто виноват) → действие → адресат.** Не заполнены все
пять — блок не нужен на слайде.
