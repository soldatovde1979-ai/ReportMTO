> целевое решение — держать значение вне книги, а в `Variable` хранить ссылку. С v7.1 основной
> путь — переменная окружения `AI_API_KEY` либо `%APPDATA%\ReportMTO\deepseek.key`; лист остаётся
> legacy-путём с предупреждением в лог.

**Чтение ключей:** `modMain.GetVariable(key)` (обязательный ключ, при отсутствии — ошибка) и
`modMain.GetVariableDef(key, default)` (необязательный ключ со значением по умолчанию).

### 1.2 Параметр `prmSourcePath` (НЕ лист `Variable`, НЕ именованный диапазон Excel)

Путь к выбранному JSON-файлу передаётся из VBA в Power Query не через лист `Variable` и не через
`Name Manager`, а через отдельный Power Query-запрос с именем `prmSourcePath` — обычную query,
созданную как «Пустой запрос» с телом-строкой (`= "C:\путь\файл.json"`), либо как формальный
Parameter через Manage Parameters. Она живёт в коллекции `ThisWorkbook.Queries`, а не
`ThisWorkbook.Names`.

- **Читает:** `Query-ImportJSON.pq` — `Source = Json.Document(File.Contents(prmSourcePath), 65001)`,
  bare-обращение по имени к другой query (как и к `fnNormalizeFields` и остальным).
- **Пишет:** `modMain.bas`, приватная функция `SetSourcePathParameter`.
- **⚠️ Значение пишется ТОЛЬКО вместе с meta-записью** (правка v5 M-1):
  ```vba
  ThisWorkbook.Queries("prmSourcePath").Formula = """" & safePath & """" & _
      " meta [IsParameterQuery=true, Type=""Text"", IsParameterQueryRequired=true]"
  ```
  Голый строковый литерал «разжалует» `prmSourcePath` из параметра в обычный запрос, и Formula
  Firewall начинает отклонять обновление `Query-ImportJSON` (запрос одновременно ссылается на другую
  query и обращается к `File.Contents`). Разжалование происходит при КАЖДОЙ загрузке, поэтому первый
  прогон после сборки может пройти, а следующий — нет. **То же правило действует для внешней
  автоматизации:** скрипты, меняющие параметр через COM (`tools/run_load_and_report.ps1`,
  `tools/run_v8.0_full.ps1`), обязаны писать meta-суффикс.
- **⚠️ История находки:** первая версия кода ошибочно меняла
  `ThisWorkbook.Names("prmSourcePath").RefersTo` — это не влияло на значение, которое видит
  `Query-ImportJSON`. Найдено при первом реальном прогоне сборки в Excel.
- **Порядок создания при сборке книги:** `prmSourcePath` должна существовать в книге **до** создания
  `Query-ImportJSON` — иначе Advanced Editor выдаёт `[Expression.Error] Импорт prmSourcePath не
  соответствует ни одному из экспортов`.

### 1.3 Вспомогательные запросы — `qExistingData.pq`, `qDiagImport.pq`, `qKeepWeeks.pq`

- **`qExistingData.pq`** — читает текущее содержимое `tbDATA` через `Excel.CurrentWorkbook()`.
  Выделен отдельным запросом, потому что Power Query не позволяет одному запросу в одном теле
  читать и файл-источник (`File.Contents`), и книгу (`Excel.CurrentWorkbook`) — это было причиной
  затронутого в `audit-src-v2.md` архитектурного тупика. Загружается ТОЛЬКО как подключение
  («Только создать подключение»), не на лист. В v6.1 добавлен отсев одной пустой строки,
  которую Excel всегда оставляет в `ListObject` после удаления всех данных из таблицы (иначе
  она проходит `LeftAnti` в `fnUpsert` как «несовпавшая старая» и копится в `tbDATA` при каждой
  повторной очистке/загрузке). Отбор — по непустому вычисляемому `Key`, а не по «все поля пустые».
- **`qDiagImport.pq`** — диагностический запрос, в сборку и в `tbDATA` не входит и данные не
  меняет. Пошагово показывает: число записей и полей в выгрузке, поля, потерянные при выборке
  первых 1000 записей (см. §2.1 «допущение о фиксированной схеме»), реальные написания
  `ready_for`/`arm`, число нераспознанных `status_date`, фактический тип `in_bounds`, число
  дублей `Key` внутри одного файла.
- **`qKeepWeeks.pq`** — читает ключ `DATA/KEEP_WEEKS` с листа `Variable` для шага ретеншна
  в `Query-ImportJSON`. Отдельный запрос по той же причине, что и `qExistingData`.

## 2. Схема персистентных данных

### 2.1 `tbDATA` (ListObject) — состав полей

> **Сверено 10.09.2026** с пятью реальными выгрузками (`data/sppr_tablet_*.json`, от 08.09 и 10.09)
> и с исходником 1С `src/1C/export2mto.bsl`. Формат раздела изменён с JSON Schema на таблицы:
> 28 полей источника в схеме нечитаемы, а группировка по уровню данных (см. §2.5) важнее типа.
>
> **Единица строки — событие подписания:** наряд × дирекция × статус. На один наряд приходится
> **ровно 4 строки** (ДГМ/ДЭНТ × приёмка/выбытие). Проверено: 4976 строк = 1244 наряда × 4.

> ⚠️ **`odometer` / `engine_hours` — две открытые проблемы.**
> 1. **Взаимоисключающи:** колёсная техника пишет пробег, тягачи и погрузчики — моточасы.
>    Проверено: одновременно заполнены у 24 строк из 4976 (0,5 %), пустых одновременно нет.
>    Признака источника в выгрузке нет — определять по тому, какое поле непусто.
> 2. **Расхождение с исходником.** По `export2mto.bsl` (стр. 52–53, 70–71) это срез последних
>    по паре (`ОбъектОФ`, тип счётчика), то есть внутри одной машины значение обязано быть
>    константой. **Фактически меняется** у 105 машин из 519 по пробегу и у 161 по моточасам.
>    Значит выгрузку делала другая версия функции. Наработку между ремонтами по этим полям
>    считать нельзя ни в одной трактовке.

### 2.2 Реализация вычисляемых полей (Power Query Custom Functions)

Рабочий код — в `src/powerquery/`; ниже суть контрактов (**при расхождении верен код**).

> **Контракт `fnNormalizeFields`: `(table) → table`** (Core §5.1). Функция отвечает не только за
> `postN`, но и за типизацию: без неё `date`/`status_date` остаются текстом, `deltaHours` не
> вычисляется, а VBA-разбор дат падает с `Type mismatch`.
>
> **v5 (N-1):** даты больше не роняют запрос. Жёсткое `Table.TransformColumnTypes` с культурой
> `en-US` превращало русский формат («26.10.2025 13:50:25») и пустую строку в ошибку ячейки,
> ошибка протекала в `fnComputeKey` и в вычитание дат. Приведение сделано терпимым.
>
> **v6 (N-3):** выгрузка 2026 убрала `day/month/year/week_status`. Раньше `yearWeek` собирался
> только из них, и при их отсутствии VBA-слой падал на `ColIndex("year_status")`
> (Err −2147221502). Теперь при отсутствии полей они вычисляются из `status_date`; если выгрузка
> отдаёт старые поля — используются они.
>
> **v7 (T1 ТЗ v1.2):** добавлены `dateWeek`, `dateMonth`, `isSigned` — только при наличии исходных
> колонок `date` / `arm`.

```m
// fnComputeGroupMetrics — вход/выход: вся таблица (после добавления Key)
(tbl as table) as table =>
    let
        Grouped = Table.Group(tbl, {"number", "direction"}, {{"GroupRows", each _, type table}}),
        WithDelta = Table.TransformColumns(Grouped, {"GroupRows", each
            let
                g = _,
                // ВНИМАНИЕ: «приемке» через «е» — см. §2.1, поле ready_for
                startRows = Table.SelectRows(g, each [ready_for] = "Готов к приемке" and [status_date] <> null),
                endRows   = Table.SelectRows(g, each [ready_for] = "Готов к выбытию" and [status_date] <> null),
                tStart = if Table.IsEmpty(startRows) then null else List.Min(startRows[status_date]),
                tEnd   = if Table.IsEmpty(endRows)   then null else List.Max(endRows[status_date]),
                delta  = if tStart = null or tEnd = null then null
                         else try Duration.TotalHours(tEnd - tStart) otherwise null
            in
                Table.AddColumn(g, "deltaHours",
                    each if [ready_for] = "Готов к выбытию" then delta else null, type nullable number)
        }),
        Result = Table.Combine(WithDelta[GroupRows])
    in
        Result
```

```m
// fnUpsert — CORE, generic. Полная замена совпавших по Key строк.
(newData as table, existingData as table) as table =>
    let
        NewBuf = Table.Buffer(newData),
        Aligned = Table.SelectColumns(existingData, Table.ColumnNames(NewBuf), MissingField.UseNull),
        UnmatchedOld = Table.NestedJoin(Aligned, {"Key"}, NewBuf, {"Key"}, "m", JoinKind.LeftAnti),
        Cleaned = Table.RemoveColumns(UnmatchedOld, {"m"}),
        Result = Table.Combine({NewBuf, Cleaned})
    in
        Result
```

> **`fnUpsert` накапливает, а не перезаписывает.** Загрузка нескольких файлов подряд копит данные,
> и новые строки ЗАМЕЩАЮТ старые с тем же `Key`. Отсюда два следствия для автоматизации:
> 1. **Порядок загрузки решает победителя** — грузить от старой выгрузки к свежей, иначе свежий
>    статус наряда затрётся старым. Проверено на паре выгрузок 08.09 и 10.09: 3756 общих `Key`,
>    из них **212 строк (5,6 %) изменились** — 212 сменили `TekStatusPoDoc`, 140 получили
>    `zn_closed`, 130 получили подпись (`status_date` и `arm`). Загрузка в обратном порядке
>    вернула бы эти наряды в устаревшее состояние. `fnDedupByKey` обеспечивает уникальность
>    `Key` только ВНУТРИ одного файла.
> 2. **Ретеншн срабатывает после upsert** и считает отсечку от самой свежей даты в ИТОГОВОЙ
>    таблице, а не от «сегодня». При маленьком `DATA/KEEP_WEEKS` накопленное молча обрежется.

### 2.4 Базовый фильтр блоков

**Базовый фильтр: `arm <> ""`.** Применяется в коде агрегации (`modAggregate`, параметр `filters`),
а не областью страницы сводной.

> ⚠️ **`in_bounds` из базового фильтра УДАЛЁН (10.09.2026).** Ранее здесь стояло
> `in_bounds = ИСТИНА`. Это было неверно и искажало главную метрику отчёта.
>
> Формула поля (`export2mto.bsl`, стр. 211–215):
> ```
> ВЫБОР КОГДА МАКСИМУМ(шхОтметкиЧекинВЗаказНарядах.Период) < &Дата1 ТОГДА ИСТИНА ИНАЧЕ ЛОЖЬ КОНЕЦ
> ```
> То есть «последняя отметка чекина раньше начала периода отбора». К качеству данных и к
> дисциплине подписания отношения не имеет. Хуже: если отметок чекина нет вообще, максимум даёт
> `NULL`, сравнение не выполняется и поле становится `ЛОЖЬ`. **Чекин — это планшет**, значит
> `in_bounds = ЛОЖЬ` у всей работы на ПК и у всех неподписанных событий. Фильтр
> `in_bounds = ИСТИНА` вычёркивал из отчёта о доле планшетов именно ту часть, ради которой отчёт
> и делается.
>
> Поле остаётся в списке обязательных колонок (`ValidateRequiredColumns`) как служебное, но
> **фильтровать и группировать по нему нельзя**. Целевое решение — попросить 1С убрать поле из
> выгрузки.

| Блок | Строки | Столбцы | Значения | Доп. фильтр | Реализация |
|---|---|---|---|---|---|
| 1 | `direction → arm` | `yearWeek` | `Count(Key)` + строка `% планшет` по каждой неделе и дирекции | `arm ∈ {ПК, ПЛАНШЕТ}` | `modAggregate.GroupCount` + `BuildBlock1Table` |
| 2 | `direction → postN` | — | `Count(Distinct number)` | — | `modAggregate.GroupCountDistinct` |
| 3 | (KPI) | — | Всего ЗН за `WEEKS_WINDOW` последних недель, присутствующих в данных; `% планшет` ДГМ/ДЭНТ текущей недели; Δ к предыдущей | `arm ∈ {ПК, ПЛАНШЕТ}` для долей | `GroupCount`/`GroupCountDistinct` в `BuildBlock3KPI` |
| 4 | `direction` | `yearWeek` | `% планшет` (доля, не Count) | `arm ∈ {ПК, ПЛАНШЕТ}` | `BuildPctMatrixTable("direction")` |
| 5 | `postN` | `yearWeek` | `% планшет` (доля, не Count) | `arm ∈ {ПК, ПЛАНШЕТ}` | `BuildPctMatrixTable("postN")` |
| 6 | `employee` | — | `% планшет`, `Count(number)`, `Average(deltaHours)`, сортировка по `% планшет` | `Count ≥ REPORT/MIN_RECORDS`; для `deltaHours` дополнительно `ready_for = «Готов к выбытию»` | `GroupCount`/`GroupAverage`/`SortDictionaryKeysByValue` |
| 7 | пары ДГМ↔ДЭНТ по одному `number` | `yearWeek` | средняя разница `status_date` «Готов к выбытию», часы + число пар | — | `BuildSyncPairs` + `SyncAggregate(False)` |
| 8 | то же | `yearWeek × postN` | то же | — | `BuildSyncPairs` + `SyncAggregate(True)` |
| 9 | `zn_type` | `defekt_type` | `Count` | — | `modAggregate.GroupCount` + `BuildBlock9Table` |

> ⚠️ **Блоки 7 и 8 неизмеримы по построению данных.** В документе ЗН **одно поле даты на обе
> дирекции**: `т1кДатаПриемки` и `т1кДатаВыдачи`. Различаются только сотрудники —
> `т1кПринялВПриемку` против `т1кСдалВПриемку`. Разность подписей равна нулю во всех 11 576 парах
> выбытия и 11 593 парах приёмки. Метрика «синхронность дирекций» показывает ноль не потому, что
> дирекции синхронны, а потому, что измерять нечего.

> **PivotTable в направлении МТО не используется** (с 24.08.2026). Все девять блоков считаются
> через generic-модуль Core `modAggregate.bas` (снимок `DataBodyRange.Value2`, карта колонок,
> фильтры, группировки) и рендерятся в HTML generic-функциями матрицы в `modContentMTO.bas`.
> Скрытый лист `Pivots` не нужен.

**Формат ключей словарей `modAggregate`:** значения группировки, соединённые `|`, с завершающим
разделителем: `GroupCount(Array("direction","yearWeek"))` → `"ДГМ|202643|"`. Булевы значения
нормализуются к `True`/`False` независимо от локали.

### 2.5 Уровни полей: чего нельзя делать с `tbDATA`

Строка `tbDATA` — это **событие подписания**, а не наряд и не машина. Поля уровня наряда и уровня
машины физически повторяются в каждой из 4 строк наряда. Отсюда жёсткие правила:

- **Суммировать `cost_parts`, `cost_Trudozatrat`, `hourdlit` по строкам `tbDATA` нельзя** — сумма
  получится **вчетверо больше** реальной. Считать только по свёртке до `number`.
- **Считать машины по строкам нельзя** — `COUNT(DISTINCT vehicle_number)` корректен,
  `COUNT(vehicle_number)` бессмыслен.
- Метрики трека A (дисциплина) считаются по событиям — это их естественная единица.
  Метрики трека B (операционка ремзоны) считаются по нарядам, заездам и машинам, поэтому
  `modContentZone` строит собственные уровни `tbZN` → `tbVisits` за один проход по снимку.
- **Метрика повторов на одном `defekt_type` недостоверна**: 15 значений — это разделы, а внутри
  раздела лежат разные отказы. Годится как верхняя граница числа кандидатов, не как факт.

### 3.1 Контракт запроса к DeepSeek

`POST https://api.deepseek.com/chat/completions`, `Authorization: Bearer <ключ>`,
таймаут 60 сек, без ретраев. Ключ резолвится `modMain.ResolveAiApiKey`: переменная окружения
`AI_API_KEY` → `%APPDATA%\ReportMTO\deepseek.key` → лист `Variable` (legacy, с предупреждением).
Ключ не пишется ни в лог, ни в HTML.

**Системное сообщение (дословно):**
```
Ты ведущий аналитик данных. Проанализируй предоставленные агрегированные метрики использования
планшетов в МТО (доля планшетов по дирекциям, ремзонам и синхронность). Сформируй краткие бизнес-выводы
(до 4 предложений на каждый) для 3-х слайдов. Ищи аномалии. Не используй данные, которых нет во входном
JSON. Ответ строго в формате JSON: {"slide3_conclusions": "...", "slide4_conclusions": "...",
"slide5_conclusions": "..."}, без markdown-разметки вокруг JSON.
```

Дополнительные поля тела запроса: `"temperature": 0.2`, `"response_format": {"type": "json_object"}`.

**Пользовательское сообщение** — JSON, собранный из словарей `modAggregate` **по белому списку полей**:

```json
{
  "block4_percent_by_direction": [{"row":"ДГМ","week":"43","total":120,"tablet":50,"pct":0.417}],
  "block5_percent_by_post":      [{"row":"СТК","week":"43","total":80,"tablet":31,"pct":0.388}],
  "block7_sync_by_week":         [{"week":"43","avg_hours":7.20,"pairs":34}],
  "block8_sync_by_week_post":    [{"week":"43","post":"СТК","avg_hours":9.10,"pairs":12}],
  "block9_defect_types":         [{"zn_type":"Внеплановый ремонт","defekt_type":"","count":57}]
}
```

**Белый список полей промпта:** `direction`, `postN`, подпись недели, счётчики, доли, `zn_type`,
`defekt_type`, часы расхождения, число пар. **Блок 6 (`employee`, ФИО) и поле `defect_desc`
не включаются никогда.**

**Все цифры считает VBA/PQ.** ИИ интерпретирует уже готовые числа: никаких расчётов, прогнозов
и суждений о людях на стороне ИИ.

Экранирование строк — полный `JsonEscape`: `\\`, `\"`, `\n`, `\r`, `\t`, `\b`, `\f` и все
управляющие символы < 0x20 в виде `\uXXXX`. Названия постов и дефектов из 1С могут содержать
перевод строки — без этого тело запроса становилось невалидным и провайдер отвечал HTTP 400.

**Транспорт:** заголовок `Content-Type: application/json; charset=utf-8`, тело отправляется байтовым
массивом UTF-8, ответ читается из `responseBody` как UTF-8. HTTP только через `CreateObject`,
без References.

### 3.2 Контракт ответа DeepSeek (обязателен, часто пропускается)

```json
{
  "type": "object",
  "properties": {
    "slide3_conclusions": { "type": "string", "description": "До 4 предложений, вывод по % планшет по дирекциям" },
    "slide4_conclusions": { "type": "string", "description": "До 4 предложений, вывод по постам ремзоны" },
    "slide5_conclusions": { "type": "string", "description": "До 4 предложений, вывод по синхронности дирекций" }
  },
  "required": ["slide3_conclusions", "slide4_conclusions", "slide5_conclusions"]
}
```

**Разбор ответа — двухшаговый** (иначе не работает вовсе): у Chat Completions ответ имеет вид
`{"choices":[{"message":{"content":"{\"slide3_conclusions\": \"...\"}"}}]}`, то есть целевой JSON
лежит строкой внутри `content` и все его кавычки экранированы.

1. `content = ExtractJsonStringValue(responseText, "content")` — внешний уровень;
2. `content = JsonUnescape(content)` — развернуть `\"`, `\\`, `\n`, `\r`, `\t`, `\uXXXX`;
   при необходимости снимается обёртка ```` ```json ````;
3. три ключа `slideN_conclusions` ищутся уже в развёрнутом тексте.

Поиск закрывающей кавычки учитывает чётность предшествующих обратных слэшей. Если `content`
не найден — предпринимается попытка разобрать `responseText` как целевой JSON напрямую.
**Деградация:** если по ключу `"slideN_conclusions"` не находится закрывающая кавычка/скобка (ответ обрезан
по лимиту токенов и т.п.) — для этого слайда подставляется заглушка «Внешний ИИ недоступен, показатели
см. в таблицах выше»; остальные распознанные слайды используют полученный текст. Неуспех ИИ
НЕ блокирует выдачу отчёта.

## 4. Открытые вопросы к 1С

| Вопрос | Почему важно |
|---|---|
| **Какой версией функции сделаны выгрузки в `data\`?** `export2mto.bsl` пишет `day/month/year/week_status` и не пишет `post_raw`; в выгрузках всё наоборот | Пока не сверено, `post_raw` нельзя использовать в отчётности, а поведение счётчиков непредсказуемо |
| **`odometer` / `engine_hours`**: по исходнику это срез последних на момент выгрузки, фактически значение меняется внутри одной машины | Определяет, можно ли считать наработку между ремонтами |
