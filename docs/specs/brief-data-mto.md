# Данные МТО: предметная область, схема, ограничения

Документ для внешнего аналитика. Задача — предложить варианты отчётов. Процесс загрузки
данных намеренно опущен: он к делу не относится.

---

## 1. Что это за организация и что происходит с техникой

Аэропорт. Собственный парк наземной техники: автотранспорт, тягачи, погрузчики,
спецмашины (обмывочные, деайсеры). Техника ломается, её чинят в собственной ремзоне.

В ремонте участвуют **две дирекции**, и это ключевая особенность:

- **ДГМ** — дирекция главного механика, владелец ремзоны, выполняет ремонт.
- **ДЭНТ** — дирекция эксплуатации наземной техники, владелец техники, сдаёт её в ремонт
  и принимает обратно.

Каждый ремонт оформляется **заказ-нарядом (ЗН)** в 1С:ERP, модуль EAM. Один ЗН = один
дефект. Машина с тремя дефектами получает три наряда.

Наряд проходит два статуса, и **каждый статус подписывают обе дирекции независимо**:

| Статус | Смысл | Кто подписывает |
|---|---|---|
| Готов к приемке | техника передана в ремзону | ДГМ и ДЭНТ, по отдельности |
| Готов к выбытию | ремонт завершён, техника возвращается | ДГМ и ДЭНТ, по отдельности |

Отсюда **4 строки на каждый заказ-наряд**: 2 статуса × 2 дирекции. Это норма выгрузки,
а не дублирование.

Подписание делается либо с **ПК**, либо с **планшета** прямо у машины. Руководство
внедряет планшеты и хочет видеть, как идёт переход.

## 2. Два независимых трека отчётности

Их нельзя смешивать: разные адресаты, разные единицы счёта.

### Трек А — дисциплина использования планшетов

**Единица счёта: событие подписания** (строка данных).
**Адресат:** руководство дирекций, ИТ-служба, внедряющая планшеты.
**Вопрос:** какая доля подписаний делается с планшета, а не с ПК, и как она меняется.

### Трек Б — операционка ремзоны

**Единица счёта: заказ-наряд, заезд, единица техники.**
**Адресат:** главный механик, руководители постов, планирование ремонта.
**Вопрос:** объём ремонтов, повторные заходы, хронически ломающиеся машины, простой,
очередь, возраст парка, расход материалов.

Трек А сейчас реализован. **Трек Б почти не реализован — основной простор для
предложений именно здесь.**

## 4. Схема данных

### 4.1 Поля события (одна строка = одно подписание)

**Идентификация наряда**

| Поле | Тип | Смысл |
|---|---|---|
| `number` | строка | Номер заказ-наряда, напр. `000300944` |
| `date` | дата-время | Момент создания наряда |
| `zn_type` | строка | Вид ремонта: «Внеплановый ремонт», плановый и т.д. |

**Событие подписания**

| Поле | Тип | Смысл |
|---|---|---|
| `ready_for` | строка | `Готов к приемке` / `Готов к выбытию` |
| `direction` | строка | `ДГМ` / `ДЭНТ` — чья это подпись |
| `status_date` | дата-время | Момент подписания |
| `arm` | строка | `ПК` / `ПЛАНШЕТ` / `НЕ ПОДПИСАНО` |
| `employee` | строка | ФИО инженера. **Персональные данные** |
| `emp_dep` | строка | Дирекция сотрудника по карточке (может расходиться с `direction`) |

**Место**

| Поле | Тип | Смысл |
|---|---|---|
| `post` | строка | Пост ремзоны. **Внимание: это РОДИТЕЛЬ поста** — цех или площадка, не конкретный пост. Может быть пустым |
| `Sektor` | строка | Сектор |
| `owner_dep` | строка | Подразделение-владелец техники |

**Техника**

| Поле | Тип | Смысл |
|---|---|---|
| `ts` | строка | Машина: гаражный номер + модель одной строкой |
| `model_type` | строка | Тип ТС |
| `MadeYear` | число | Год выпуска — даёт возраст парка |
| `odometer` | число | Пробег |
| `engine_hours` | число | Моточасы |

**Дефект**

| Поле | Тип | Смысл |
|---|---|---|
| `defekt_type` | строка/null | Классификатор дефекта, 12 значений |
| `defect_desc` | строка/null | Свободное описание, ~20 тыс. уникальных |
| `TekStatusPoDoc` | строка | Текущий статус по документу |

**Трудозатраты и стоимость**

| Поле | Тип | Смысл |
|---|---|---|
| `hourdlit` | строка | Плановая длительность. Приходит строкой вида `"11:00"`, не числом |
| `cost_parts` | число | Стоимость материалов, рубли |
| `cost_Trudozatrat` | число | **Часы, не рубли**, вопреки названию |

**Календарные поля**

`day_status`, `month_status`, `year_status`, `week_status` — разложение `status_date`.

### 4.2 Вычисляемые поля

| Поле | Как считается |
|---|---|
| `postN` | Нормализация `post`: содержит «стк» → `СТК`, «прк» → `ПРК`, иначе как есть |
| `yearWeek` | `year_status * 100 + week_status`, напр. `202635` — сквозная ось недель |
| `deltaHours` | Часы между самой ранней приёмкой и самым поздним выбытием по паре (наряд, дирекция) |

## 5. Трёхуровневая модель

Реализован только первый уровень. Второй и третий спроектированы, но не построены —
предложения по ним особенно интересны.

**Уровень 1 — событие.** Есть. Одна строка = одно подписание. 132 704 строки.

**Уровень 2 — заказ-наряд.** Свёртка по `number`. Одна строка = один ремонт = один
дефект. 33 176 строк. Здесь появляются длительность ремонта, стоимость, дефект, машина.

**Уровень 3 — заезд.** Склейка нарядов одной машины, приехавшей один раз. Машина с тремя
дефектами создаёт три наряда, но заезд один. Разделение «пакет» (приехала один раз,
чинили всё) и «дробление» (приезжала трижды) — по разрыву во времени. По факту
распределения порог около 12 часов: медиана размаха у заездов с несколькими нарядами
составила 12,9 часа.

**Справочники.** `dictZone` (пост → ответственный руководитель) — не создан.
`dictDefect` (описание дефекта → смысловая группа) — не создан, нужен ИИ для
классификации 20 тыс. описаний.

## 6. Технология хранения

Одна книга Excel `.xlsm` во внутреннем контуре предприятия. Без интернета, без облака,
без почты. Отчёт — статический HTML-файл в локальной папке.

| Слой | Чем реализован |
|---|---|
| Источник | JSON-выгрузка из 1С:ERP (EAM), UTF-8 |
| Хранение | Лист Excel, таблица `tbDATA`, накопительно |
| Обработка | Power Query (язык M) |
| Расчёты и сборка | VBA |
| Вывод | HTML с инлайн-CSS и JS, без внешних библиотек |
| Интерпретация | Внешняя LLM по HTTP, только текстовые комментарии |

Ограничения, влияющие на дизайн отчётов:

- Всё офлайн. Никаких CDN, шрифтов и картинок из сети. Графика — либо инлайн-SVG, либо
  встроенная библиотека.
- Все числа считает Excel. ИИ **не считает ничего** — только формулирует выводы по
  готовым агрегатам. Прогнозы и суждения о конкретных людях ИИ не делает.
- ФИО инженеров **не передаются** во внешнюю LLM (152-ФЗ). В промпт уходят обезличенные
  агрегаты.
- Объём книги ограничен: тяжёлые пересчёты на 132 тыс. строк упираются в
  производительность.

## 7. Качество данных: что известно и проверено

**Это самый важный раздел.** Каждый пункт уже стоил ошибочных выводов. Предложение
отчёта, опирающегося на дефектное поле, бесполезно.

### Поля, которым нельзя доверять как есть

**`post` — это родитель поста, а не пост.** «СТК цех 1» и «СТК цех 2» — разные площадки,
и схлопывать их нельзя. Пустое значение неоднозначно. **33% ремонтных нарядов вообще без
поста** — это само по себе сюжет для отчёта о качестве учёта.

**`defekt_type` — это разделы, а не диагнозы.** 12 значений на 33 тыс. нарядов. Любая
метрика повторных ремонтов, построенная только на нём, недостоверна: «Электрооборудование»
второй раз за месяц не означает тот же дефект. Осмысленная группировка требует обработки
`defect_desc` (~20 тыс. текстов) — это отдельный слой, которого пока нет.

**`deltaHours` меряет не ремонт.** Это время от приёмки до подписания выбытия, куда входят
очередь, ожидание запчастей и задержка подписи. Для «плана против факта» непригодно
полностью: наряд с планом 2,4 часа показывает факт 5 042 часа. Отделить очередь от
ремонта можно только при наличии истории смены поста, а есть ли она в 1С — пока не
выяснено.

**`odometer` и `engine_hours` взаимоисключающи.** Колёсная техника пишет пробег, тягачи и
погрузчики — моточасы. Нужен признак, какой счётчик применим, иначе любая метрика
наработки будет считать среднее по несопоставимым величинам.

**`cost_Trudozatrat` — часы, а не рубли**, несмотря на название. Считать стоимость
повторных ремонтов в деньгах можно только по `cost_parts` (материалы).

**`in_bounds` в реальной выгрузке всегда `false`** — фильтр по нему обнуляет выборку.
Поле подлежит удалению.

**`week/month/year_status = 1` при пустой `status_date`.** Даёт `yearWeek = 101` —
строку-призрак на оси недель. Это маркер незакрытого дефекта выгрузки.

**`model_type` — константа «Автотранспорт»** для всех записей. Как измерение бесполезно.

**`hourdlit` приходит строкой `"11:00"`**, не числом — требует разбора.

**`arm = "ПК"` включает случаи отсутствия отметки.** Владелец процесса решил считать это
фактом: расхождение подписанта и отметки само по себе нарушение.

**`defect_desc` может содержать ФИО** — санитайзер перед отправкой в LLM не написан.

### Историческая ловушка

Статусы в данных пишутся **через «е»**: «Готов к приемке». Сравнение через «ё» не находит
ни одной строки. Из-за этой опечатки `deltaHours` не вычислялся никогда и весь столбец
был пуст, без единой ошибки в логе.

## 8. Что уже построено

Чтобы не предлагать существующее. Всё перечисленное — трек А.

| Блок | Содержание |

## 9. Что уже видно в данных

Результаты прогона на полной истории. Это подсказки, а не готовые отчёты.

- **Тренд планшета:** рост с 30% в январе до 60–72% в августе. У ДЭНТ резкий скачок в
  июне. Главный сюжет трека А.
- **Хроники:** машина `28-19` простояла 1 245 часов за восемь месяцев; `28-18` заезжала
  157 раз.
- **Возраст парка:** до 14 лет — около 37 заездов на машину, после 15 лет — 52. Материалы
  растут с 5,6 тыс. до 333 тыс. рублей на единицу. Кривая явно нелинейная.
- **Парето по узлам:** ходовая, электрика и ДВС дают 61% заездов.
- **Качество учёта:** 33% ремонтных нарядов без указания поста.
- **Повторные заходы:** насчитано 42%, но это артефакт классификатора из 12 значений.
  Настоящая цифра неизвестна.

## 10. Что требуется от вас

Предложить варианты отчётов, преимущественно по **треку Б** (операционка ремзоны) —
он практически не покрыт.

По каждому предложению желательно указать:

1. **Вопрос**, на который отчёт отвечает, и **кто** его задаёт.
2. **Единицу счёта** — событие, наряд, заезд или машина. Смешение единиц здесь основной
   источник ошибок.
3. **Какие поля** нужны и **достаточно ли** имеющихся. Если поля дефектны (раздел 7) —
   что нужно починить в выгрузке 1С.
4. **Разрезы** — по чему группировать, какая ось времени.
5. **Что человек сделает** по результату. Метрика, не меняющая ничьё поведение, не нужна.
6. **Уровень модели** — хватает ли уровня события, или нужен наряд либо заезд.

Отдельно ценно: какие из перечисленных дефектов данных сами по себе достойны отдельного
отчёта о качестве учёта, и что из задуманного построить **нельзя** до починки выгрузки.

Ограничения помнить: офлайн-HTML, все расчёты на стороне Excel, ФИО во внешнюю модель не
уходят, оценивать людей нельзя.
