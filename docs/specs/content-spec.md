# МТО: контентная спецификация — v3.3.0

> Дополняет **`docs/spec.md`** (платформа/ETL/AI Gateway/Template Engine — общие механизмы).
> Здесь — всё, что специфично направлению «Контроль использования планшетов инженерами (ДГМ/ДЭНТ)»:
> поля источника, вычисляемые поля, 9 аналитических блоков, раскладка 6 слайдов, промпт ИИ, ПД, палитра.

---

## 1. Назначение направления

Дирекции ДЭНТ и ДГМ используют планшеты и стационарные ПК для смены статусов заказ-нарядов в 1С при
сдаче/приёмке техники. Отчётность показывает, насколько активно инженеры пользуются планшетами вместо
ПК, динамику, синхронность работы дирекций и персональную эффективность сотрудников.

**Провайдер ИИ для направления:** DeepSeek Chat Completions (`AI/PROVIDER = DeepSeek`, модель `deepseek-chat`) —
заменяет Gemini, предусмотренный исходными требованиями к отчёту; выбран на этапе пилота как доступный напрямую из
внутреннего контура без обхода блокировок (см. ../spec.md §3.3).

## 2. Источник данных и формат обмена

Имя файла: `sppr_tablet_<дата>_<время>.json`. На каждый заказ-наряд 1С формирует несколько записей
истории статусов — заказ-наряд «расщепляется» на комбинации (ЗН × дирекция × статус).

```json
[
  {
    "number": "000300944",
    "date": "2025-10-24T15:06:39",
    "ready_for": "Готов к приёмке",
    "direction": "ДГМ",
    "status_date": "2025-10-26T13:50:25",
    "employee": "Барыкин Илья Игоревич",
    "arm": "ПК",
    "post": "ремзона стк",
    "day_status": 26, "month_status": 10, "year_status": 2025,
    "week_status": 43,
    "zn_type": "Внеплановый ремонт",
    "emp_dep": "ДГМ",
    "model_type": "Автотранспорт",
    "in_bounds": true,
    "defekt_type": null,
    "defect_desc": null
  }
]
```

**Поля выгрузки, добавленные в 2026 (v3.3):** в актуальных файлах `sppr_tablet_*.json` появились
реквизиты, которых нет в примере выше:

| Поле | Тип в выгрузке | Назначение |
|---|---|---|
| `owner_dep` | текст | подразделение-владелец ТС (например «Служба доставки пассажиров (ДЭНТ)») |
| `TekStatusPoDoc` | текст | статус ЗН по документу (например «В ремонте») |
| `vehicle_group` | текст | группа ТС (например «Микроавтобус») |
| `vehicle_number` | текст | номер ТС (например «5-26») |
| `hourdlit` | текст (`чч:мм`) | длительность работ; приходит текстом, не числом |
| `MadeYear` | текст (ISO datetime) | дата выпуска ТС (например `2017-12-01T00:00:00`) |
| `Sektor` | текст | сектор/линейка (например «Линейка Ш-1») |
| `cost_parts` | число | стоимость запчастей |
| `cost_Trudozatrat` | число | стоимость трудозатрат |
| `ts` | текст | описание ТС (например «5-26 Микроавтобус FORD TRANSIT») |
| `zn_closed` | datetime/null | дата закрытия ЗН, может быть `null` |
| `odometer` | число | пробег |
| `engine_hours` | число | моточасы |

Новые поля в расчёты блоков 1–9 не входят и проходят выгрузку без изменений; их использование —
план v4 (отдельная задача).

**Третье значение `arm`:** в выгрузке 2026 встречаются строки со статусом «НЕ ПОДПИСАНО»
(`arm = «НЕ ПОДПИСАНО»`, `employee` и `status_date` пустые, `in_bounds = false`). Такие строки
отсекаются базовым фильтром и в отчётность не входят (см. §5).

**Формат сообщения об ошибке** (лист `Logs`): Дата | Тип записи | Действие | Источник | Результат.

## 3. Схема `tbDATA` направления МТО

Поля JSON (раздел 2) без изменений + вычисляемые поля:

| Поле | Логика расчёта | Реализация (Function Contract ../spec.md §6.2) |
|---|---|---|
| `postN` | Нормализация поста: если `post` содержит «стк» (без учёта регистра) → `«СТК»`; если содержит «прк» → `«ПРК»`; иначе `postN = post` без изменений | `fnNormalizeFields` |
| `Key` | `[number] & "\|" & Text.From([date]) & "\|" & [ready_for] & "\|" & [direction]` | `fnComputeKey` |
| `yearWeek` | `year_status * 100 + week_status` (например `202643`). Используется для группировки и сортировки недель; на экран выводится номер недели, а при данных за несколько лет — `неделя/год` | `fnNormalizeFields` |
| `deltaHours` | См. п. 3.1 ниже | `fnComputeGroupMetrics` |

> `yearWeek` добавлен в v3.2 (ревью, P1-4): `week_status` без года схлопывал неделю 43/2025 и 43/2026
> в одну колонку, а вычисление окна `currentWeek − N + 1` давало отрицательные номера на границе года.

#### Поля плана v4 — гипотезы (⚠️ требуют подтверждения заказчиком)

В документах проекта упоминаются «семь вычисляемых полей плана v4», но по именам известны пять.
Правила их формирования нигде не зафиксированы; ниже — рабочие гипотезы по смыслу названий и
фактическим данным выгрузки 2026. Все пять — кандидаты в `fnNormalizeFields`, в коде пока
не реализованы.

| Поле | Тип | Гипотеза расчёта | Кандидат-источник в выгрузке |
|---|---|---|---|
| `isWait` | boolean | ЗН в ожидании (простой: запчасти/подрядчик/решение); `TekStatusPoDoc` содержит «ожидан» (без учёта регистра) | `TekStatusPoDoc` |
| `isRepair` | boolean | ЗН относится к ремонту (не ТО/обслуживание); `zn_type` содержит «ремонт» (без учёта регистра) | `zn_type` |
| `usage` | не определён | Признак использования планшета. Гипотеза A: `arm = «ПЛАНШЕТ»` (дублирует `arm`); Гипотеза B: числовой показатель использования. Формула без дополнительных данных не выводится | `arm` / `emp_dep` |
| `usageSrc` | текст (гипотеза) | Источник, из которого определён `usage` (например «1С», «журнал входа в планшет»); способ вывода значения неясен | — |
| `ageYears` | число | Возраст ТС в годах на момент формирования отчёта: `Year(сейчас) − Year(MadeYear)`; округление (полные годы vs календарный год) не определено | `MadeYear` |

Названия оставшихся двух полей из «семи» в проекте не зафиксированы.

Эти три функции — единственное, что Core ожидает от направления по контракту из ../spec.md §6.2
(фиксированные имена и сигнатуры); их реализация ниже специфична МТО.

### 3.1 Реализация функций (Power Query M-код)

Рабочий код — в файлах проекта (не дублируется здесь во избежание рассинхрона):
`src/powerquery/fnNormalizeFields.pq`, `src/powerquery/fnComputeKey.pq`,
`src/powerquery/fnComputeGroupMetrics.pq`.

> ⚠️ **Контракт `fnNormalizeFields` изменён в v3.2: `(table) → table`** (../spec.md §6.2, A-3 ревью).
> Функция теперь отвечает не только за `postN`, но и за **типизацию** полей
> (`Table.TransformColumnTypes(..., "en-US")`): без неё `date`/`status_date` оставались текстом,
> `deltaHours` не вычислялся никогда, а `BuildSyncPairs` падал с `Type mismatch`.
> `post` может быть `null` — нормализация выполняется по `post ?? ""`.
>
> Код по-прежнему не прогонялся целиком в редакторе Power Query — при внедрении проверить
> синтаксис `Table.Group`/`Table.TransformColumns` в реальном редакторе.

**Логика `deltaHours`:** группировка по `(number, direction)` → `tStart` = `status_date` записи
`«Готов к приёмке»`, `tEnd` = `status_date` записи `«Готов к выбытию»` → `deltaHours =
Duration.TotalHours(tEnd − tStart)`, присваивается **только строке `«Готов к выбытию»`**
(считаем, что длительность ремонта относится к инженеру, зафиксировавшему закрытие наряда) —
у строки `«Готов к приёмке»` поле остаётся `null`.

> ⚠️ Предположение: если в рамках одной дирекции на один `number` приходится больше двух статусных
> записей (в исходном примере данных на один `number` в рамках дирекции приходилось ровно две —
> «Готов к приёмке» и «Готов к выбытию»), функция берёт `min(status_date)` среди записей
> «Готов к приёмке» и `max(status_date)` среди записей «Готов к выбытию». Если это не так —
> требуется уточнение у заказчика.

## 5. Определения аналитических блоков (1–9)

**Общий фильтр для всех блоков, если не указано иное:** `in_bounds = ИСТИНА`, `arm <> ""`.

Строки `arm = «НЕ ПОДПИСАНО»` в выгрузке 2026 идут с `in_bounds = false` и базовым фильтром
не пропускаются — отдельная проверка по `arm` для них не нужна.

> Фильтр применяется **в коде агрегации** (`modAggregate`, параметр `filters`), а не областью
> страницы сводной таблицы. До v3.2 фильтр передавался в PivotTable как `xlPageField` и
> фактически не применялся — поле оставалось в значении «(Все)» (ревью, P1-1).

### Блок 1 — Свод по неделям и постам (Отчёт №4)
Строки: `direction → arm`; столбцы: `week_status`; значения: `Count(Key)`.
Доп. строка «% планшет» = `Count(arm="ПЛАНШЕТ") / Count(arm∈{ПК,ПЛАНШЕТ})` по каждой неделе и дирекции.
Фильтр: `arm ∈ {ПК, ПЛАНШЕТ}`. Раскраска строки «% планшет» — палитра из раздела 9.
→ Воспроизводит структуру исходного примера сводной таблицы: строки «Дирекция → ARM»
(ДГМ/ДЭНТ × ПК/ПЛАНШЕТ), столбцы — недели за последние 8 недель, значения — количество записей,
дополнительная строка «% планшет» (= ПЛАНШЕТ / (ПЛАНШЕТ + ПК)) с раскраской
«чем больше — тем зеленее, чем меньше — тем краснее».

### Блок 2 — Количество ремонтов по постам ремзоны (Отчёт №3)
Строки: `direction → postN`; значения: `Count(Distinct number)` (уникальных заказ-нарядов, не строк).
Фильтр: базовый.

### Блок 3 — Общие показатели (KPI текущей недели/окна)
Разовые агрегаты верхнего уровня: всего ЗН обработано за окно `REPORT/WEEKS_WINDOW`, `% планшет` по
ДГМ и по ДЭНТ за текущую неделю, тренд к предыдущей неделе (Δ п.п.). Набор фиксируется в коде на
этапе пилота (не пересчитывается диалогом с ИИ при каждом запуске) — согласовывается с заказчиком один раз.

### Блок 4 — Динамика `% планшет` по дирекциям (по неделям)
Строки: `direction`; столбцы: `week_status`; значение: `% планшет`.
Источник для gauge-индикатора Слайда 3 и для промпта ИИ (`slide3_conclusions`).

### Блок 5 — Динамика `% планшет` по постам ремзоны (по неделям)
Строки: `postN`; столбцы: `week_status`; значение: `% планшет`.
Источник для Слайда 4 (вместе с Блоком 2) и промпта ИИ (`slide4_conclusions`).

### Блок 6 — Рейтинг инженеров (Отчёты №1 и №5)
Строки: `employee`; значения: `% планшет`, `Count(number)` обработанных нарядов,
`Average(deltaHours)` — средняя длительность ремонта по закрытым нарядам инженера.
Сортировка по убыванию `% планшет`.
**Вывод на слайд:** первые `TOPN` строк (по умолчанию 10, см. `Variable/REPORT/TOPN`) — «отличники»,
последние `TOPN` строк — «двоечники». `TOPN` вынесен в `Variable`, чтобы не хардкодить «10» в коде.

**Порог значимости (v3.2, ревью P1-12):** в рейтинг попадают только сотрудники с числом записей
не менее `Variable/REPORT/MIN_RECORDS` (по умолчанию 5). Без порога инженер с одним нарядом на ПК
даёт 0,0 % и уверенно занимает верх «Требуют внимания», вытесняя тех, кто реально работает много
и мимо планшета. Для отчёта, где ФИО публикуются в открытом виде, это не статистическая мелочь,
а репутационный риск. Значение порога — согласуемое с заказчиком (см. §12).

`Average(deltaHours)` считается по тому же базовому фильтру, что и соседние агрегаты, плюс срез
`ready_for = «Готов к выбытию»` (до v3.2 фильтры внутри блока расходились — ревью, P1-14).

> ⚠️ Открыто: здесь «% планшет» исторически описывался как «текущая неделя/окно», а код считает его
> по всей истории `tbDATA`. Решение не принято — вопрос вынесен в §12 и `../plans/next-steps.md`.

### Блок 7 — Синхронность дирекций (Отчёт №2)
Сопоставление активности ДГМ и ДЭНТ по одним и тем же `number`/периодам: для каждого `number`,
присутствующего в обеих дирекциях, — разница между `status_date` записей `«Готов к выбытию»`
ДГМ и ДЭНТ (в часах). Агрегация: среднее по неделям.

### Блок 8 — Синхронность статусов (доп. разрез к Блоку 7)
То же сопоставление, но по неделям и постам одновременно — выявляет, в каких сочетаниях
пост/неделя рассинхрон между дирекциями наибольший.

### Блок 9 — Разбивка по видам ремонта/дефектов
Строки: `zn_type`; доп. срез — `defekt_type` (если заполнено); значения: `Count(number)`.
Источник для Слайда 5 (контекст к синхронности).

Реализация всех 9 блоков — в `src/vba/modContentMTO.bas`.

**С версии 3.2 ни один блок не использует PivotTable.** Все девять блоков считаются напрямую по
`tbDATA` через generic in-memory агрегатор Core `modAggregate.bas` и рендерятся в HTML
generic-функциями матрицы (`BuildBlock1Table`, `BuildPctMatrixTable`, `BuildSyncTable` и т.п.).

Обоснование отказа от Pivot для Блоков 1/4/5/9 (ревью, P1-1/P1-2/P1-3, P2-6):

- фильтры базового условия в Pivot-варианте фактически не применялись (поле уходило в область
  страницы со значением «(Все)»), а `modAggregate` фильтрует корректно;
- «% планшет» всё равно считается в VBA — из сводной он не берётся; при этом строка процентов
  физически не могла совпасть по колонкам с сеткой недель сводной;
- уходят скрытый лист `Pivots`, накопление `PivotCaches` при каждом прогоне и работа с `TableRange2`;
- сортировка недель и постов становится управляемой (`yearWeek`, явная сортировка осей);
- сериализация агрегатов в промпт делается из тех же словарей, без обхода диапазонов.

`modPivotBuilder.bas` остаётся в Core как готовый механизм для будущих направлений — правило
«не менять Core ради специфики МТО» не нарушено. Процедура `BuildPivots()` сохранила имя (оно
зафиксировано контрактом ../spec.md §14) и теперь выполняет подготовку снимка данных и сброс кэшей.

Статус реализации — см. §11.1, §11.2 и `../plans/next-steps.md`.

## 7. Спецификация внешнего обогащения (DeepSeek API)

`POST https://api.deepseek.com/chat/completions`, модель `deepseek-chat`, таймаут 60 сек, без ретраев.

**Один комбинированный запрос** на все текстовые выводы (Слайды 1–7):

Системный промпт:
> «Ты ведущий аналитик данных. Проанализируй предоставленные агрегированные метрики использования
> планшетов в МТО (доля планшетов по дирекциям, ремзонам и синхронность). Сформируй краткие бизнес-выводы
> (до 4 предложений на каждый) для 7-ми слайдов. Ищи аномалии. Не используй данные, которых нет во входном
> JSON. ФИО сотрудников во входных данных заменены маркерами вида `[EMP_12]` — не изменяй и не склоняй
> маркеры, в выводах ссылайся на сотрудников только ими. Ответ строго в формате JSON с ключами
> `slide1_conclusions` … `slide7_conclusions`, без markdown-разметки вокруг JSON.»

Дополнительно в теле запроса: `"temperature": 0.2` и `"response_format": {"type": "json_object"}`
(поддерживается DeepSeek) — снижает вариативность формулировок и повышает шанс получить валидный
JSON. Обе настройки контентные, задаются в `BuildPrompt`, а не в Core.

Пользовательское сообщение — **настоящий JSON** с агрегатами Блоков 4, 5, 7, 8, 9 и псевдонимами
Блока 6, собранный по белому списку полей:

```json
{
  "block4_percent_by_direction": [{"row":"ДГМ","week":"43","total":120,"tablet":50,"pct":0.417}],
  "block5_percent_by_post":      [{"row":"СТК","week":"43","total":80,"tablet":31,"pct":0.388}],
  "block7_sync_by_week":         [{"week":"43","avg_hours":7.20,"pairs":34}],
  "block8_sync_by_week_post":    [{"week":"43","post":"СТК","avg_hours":9.10,"pairs":12}],
  "block9_defect_types":         [{"zn_type":"Внеплановый ремонт","defekt_type":"","count":57}],
  "block6_people":               [{"emp":"[EMP_1]","pct_cur":0.917,"pct_prev":0.833,"signs":14}]
}
```

**Белый список полей промпта:** `direction`, `postN`, неделя (подпись), счётчики, доли,
`zn_type`, `defekt_type`, часы расхождения и число пар; Блок 6 — только маркеры `[EMP_N]` без ФИО
и агрегаты по людям (маркер, % планшет ПН/ПН-1, число подписаний). Всё остальное — включая
`employee` и `defect_desc` — в промпт не сериализуется (см. раздел 8).

> До v3.2 сериализация была сломана: `PivotToCompactJSON` обходил только первую строку
> `TableRange2`, то есть строку страничного фильтра — модель получала `in_bounds; (Все);`
> вместо данных, и любой ответ был галлюцинацией (ревью, P0-5).

Разбор ответа — **двухшаговый** (ревью, P0-4): сначала из `choices[0].message.content` извлекается
строка, затем разворачивается JSON-экранирование, и только потом ищутся ключи
`slide1…slide7_conclusions`. При обрезанном/невалидном ответе для нераспознанного слайда подставляется
заглушка «Внешний ИИ недоступен, показатели см. в таблицах выше».

Реализация — `src/vba/modContentMTO.bas`: `BuildPrompt()` (сборка тела запроса; сериализация через
`PctMatrixToJson`, `SyncToJson`, `Block9ToJson`, `Block6PeopleToJson`, экранирование — полный
`JsonEscape`, включая управляющие символы) и `ParseAIResponse(...)` (контракт Core, см. `modMain.bas`).
**Сигнатура контракта не меняется**: 7 ключей складываются в module-level кэш (аналог
`mPairs`/`mPairsReady`), наружу `ByRef slide3/4/5` возвращают прежние 3 значения;
`BuildPlaceholders` при пустом кэше использует входные параметры (путь `DebugGenerateOffline`).
После разбора выполняется обратная замена маркеров `[EMP_N]` → ФИО по убыванию номеров, только
в тексте ИИ-выводов.

## 11.1 Пробелы, вскрывшиеся при написании кода — статус: закрыто

Все пять пунктов реализованы в `src/vba/modContentMTO.bas` через новый generic-модуль Core
`src/vba/modAggregate.bas` (in-memory группировка/фильтрация по 2D-массиву, без Data Model):

- [x] **Блок 2** — честный `Distinct Count` по `number` через `modAggregate.GroupCountDistinct`,
      прокси-фильтр по `ready_for` больше не нужен.
- [x] **Блок 3 (KPI)** — реализован в `BuildBlock3KPI()`: всего ЗН за окно `WEEKS_WINDOW` (через
      `GroupCountDistinct` по неделям), `% планшет` ДГМ/ДЭНТ текущей недели и Δ к предыдущей.
      «Текущая неделя» определена как максимальный `week_status`, реально присутствующий в данных
      (не календарная неделя) — сознательное решение, чтобы KPI не расходился с данными при
      задержке выгрузки; при необходимости легко заменить на `DatePart("ww", Date)`.
- [x] **Блок 6 (топ/антитоп-`TOPN`)** — честная сортировка по `% планшет` через
      `modAggregate.SortDictionaryKeysByValue` (сортировка пузырьком, приемлемо для десятков-сотен
      сотрудников), `Average(deltaHours)` — через `modAggregate.GroupAverage`. См. ⚠️ в §5 —
      «текущая неделя/окно» из описания и «вся история» в коде пока расходятся.
- [x] **Блоки 7/8 (синхронность дирекций)** — реализована попарная разница `status_date` записей
      `«Готов к выбытию»` между ДГМ и ДЭНТ по одному `number` (`BuildSyncPairs()`), агрегация по
      неделям (Блок 7) и по неделям×постам (Блок 8). `postN` относится к заказ-наряду целиком
      (подтверждено), поэтому берётся из любой из двух строк без допущений — прежнее ⚠️ снято.
      Обе агрегации также сериализуются в промпт ИИ через `Block7ToCompactText`/`Block8ToCompactText`
      (см. §7 — ранее здесь была неверная пометка, что Блок 8 в промпт не попадает).
- [x] **«% планшет» в Блоках 1/4/5** — считается напрямую по `tbDATA` через `modAggregate.GroupCount`
      (не из уже построенного Pivot) и выводится отдельной раскрашенной строкой под таблицей
      (`PivotToHTMLTableWithPercent`).

Остаётся не автоматизированным (сознательно, вне контракта Core/Content Spec): `SYNC_THRESHOLD_MIN`
из `Variable` пока не используется в Блоках 7/8 — там выводится только среднее время расхождения,
а не доля нарядов, укладывающихся в порог. Если заказчику нужна именно доля/флаг «не синхронизировано» —
это независимое расширение `Block7ToCompactText`/`Block8ToCompactText`, а не пробел контракта.

## 12. Открытые вопросы / допущения (МТО-специфичные)

**В: Что если DeepSeek вернёт невалидный JSON (обрезан по лимиту токенов)?**
О: Строковый парсер мягко деградирует — для слайда без распознанного ключа подставляется заглушка,
остальные слайды используют полученный текст.

**В: Нужно ли версионировать файлы в `result\`?**
О: Да — имя файла включает дату/время (`Report_<YYYYMMDD_HHMMSS>.html`), старые отчёты не удаляются
автоматически; ротация — вне объёма пилота.

**В: `deltaHours` — если у наряда в дирекции больше двух статусных записей?**
О: См. допущение в §3.1 — берутся `min`/`max` по `status_date`; требует подтверждения заказчиком,
если такие случаи реально встречаются в данных 1С.

**В: Почему `TOPN` вынесен в `Variable`, а не зашит как 10?**
О: Чтобы будущие направления (по аналогии с МТО, см. ../spec.md §14) могли переиспользовать Блок 6
с другим размером топ-листа без изменения кода — только правкой листа `Variable`.

### 12.1 Открытые вопросы к заказчику (добавлено 24.08.2026)

- **`REPORT/MIN_RECORDS`** — порог минимального числа записей для попадания в рейтинг Блока 6.
  Предложено 5; согласовывать одним пакетом с `TOPN`.
- **«% планшет» в Блоке 6** — по всей истории (как в коде) или за `REPORT/WEEKS_WINDOW`/текущую
  неделю (как в раннем описании §5)?
- **Круговой gauge (§6)** — нужен ли он дополнительно к раскрашенной матрице, или таблицы достаточно.
- **Хранение `AI/API_KEY`** — решено кодом v7.1: значение вне книги (env `AI_API_KEY` /
  `%APPDATA%\ReportMTO\deepseek.key`); открытым остаётся только регламент ИБ по выдаче ключа.
