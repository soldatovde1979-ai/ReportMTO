Бизнес-процесс, модули и граница Core / Content Spec

Как заказ-наряд из 1С превращается в HTML-отчёт: какие модули включаются на каждом шаге, и какая часть кода — переиспользуемая платформа (Core), а какая — специфика направления МТО (Content Spec), связанные через фиксированный Function Contract.

Core — платформа (модуль ниже применим и к другим направлениям)
Content Spec — специфика МТО (9 блоков, промпт, JSON-поля)
Function Contract — вызов по фиксированному имени через границу
PII-граница — employee (ФИО) дальше не проходит

1. Бизнес-процесс: от статуса в 1С до файла в result\

Шесть шагов сверху вниз; чипы под каждым шагом — модули, которые в нём участвуют, окрашенные по владельцу (Core / Content Spec). Слева — сквозной вызов modLog.WriteLogEntry, он не привязан к одному шагу.

2. Карта модулей: Core ↔ Content Spec

Те же модули, но как граф связей, а не порядок действий. Слева — платформа Core (10 модулей: 8 VBA + 2 generic-запроса Power Query), справа — Content Spec направления МТО (модуль modContentMTO.bas как хаб, 3 M-функции, HTML-шаблон). Фиолетовые пунктирные стрелки — Function Contract: Core вызывает функцию по фиксированному имени, не зная её реализации; амбер-пунктир — обратные вызовы Content Spec в generic-инструменты Core.

3. Назначение модулей — таблица-справочник

Та же карта построчно, с кратким назначением каждого модуля.

МодульВладелецНазначение
modMain.basCoreТочка входа: две кнопки на листе Main — LoadSourceFile (загрузка JSON, обновление prmSourcePath, Refresh) и GenerateReport (оркестрация шагов 3–5).
modPQSync.basCoreСинхронный Refresh соединений Power Query — ждёт завершения обновления, прежде чем VBA продолжит читать tbDATA.
modAIGateway.basCoreHTTP-транспорт к ИИ через CreateObject("MSXML2.ServerXMLHTTP.6.0") — без ссылок на библиотеки; провайдер/модель/URL берёт только с листа Variable, ничего не хардкодит.
modHTMLEngine.basCoreШаблонизатор: подстановка {{PLACEHOLDER}} в HTML-шаблон и сохранение результата — не знает, что означают конкретные плейсхолдеры.
modPivotBuilder.basCoreGeneric-конструктор PivotTable по описанию (поля строк/значений/агрегации) — не содержит специфики МТО.
modAggregate.basCoreIn-memory агрегация поверх массива ListObject.DataBodyRange.Value2: Distinct Count, среднее по группе, сортировка по значению, попарные разницы дат — то, что PivotTable без Data Model не умеет.
modColor.basCorePercentToColor/InterpolateHex — раскраска ячеек по проценту для HTML-таблиц.
modLog.basCoreWriteLogEntry — запись в tbLogs на листе Logs; вызывается из модулей верхнего уровня на шагах 2–5.
Query-ImportJSON.pqCoreGeneric ETL-пайплайн: читает prmSourcePath, разворачивает JSON, вызывает по имени fnNormalizeFields/fnComputeKey/fnUpsert.
fnUpsert.pqCoreGeneric upsert по Key через Table.Combine — полная замена совпавших строк, не anti-join.
modContentMTO.basContent SpecХаб направления МТО: все 9 аналитических блоков, сборка промпта (без employee), разбор ответа ИИ, сборка плейсхолдеров — вызывает Core-инструменты (Pivot/Aggregate/Color/HTMLEngine).
fnNormalizeFields.pqContent SpecНормализация значения post (регистр «СТК»/«стк»/«Стк» и т.п.) — правило специфично для формата выгрузки 1С по МТО.
fnComputeKey.pqContent SpecФормула составного Key (номер заказ-наряда + направление и т.п.) — определяет, что считается «той же строкой» при upsert.
fnComputeGroupMetrics.pqContent SpecРасчёт deltaHours — попарная разница status_date между записями ДГМ/ДЭНТ, используется в Блоках 7/8.
tmp_index.htmlContent SpecHTML-шаблон отчёта — 6 слайдов, все плейсхолдеры {{BLOCK_N_...}}; автономный, без внешних CDN.
