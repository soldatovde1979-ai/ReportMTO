# МТО: контентная спецификация — v3.0.0

> Дополняет **`MTO_Architecture_Core_v3.md`** (платформа/ETL/AI Gateway/Template Engine — общие механизмы).
> Здесь — всё, что специфично направлению «Контроль использования планшетов инженерами (ДГМ/ДЭНТ)»:
> поля источника, вычисляемые поля, 9 аналитических блоков, раскладка 6 слайдов, промпт ИИ, ПД, палитра.

---

## 1. Назначение направления

Дирекции ДЭНТ и ДГМ используют планшеты и стационарные ПК для смены статусов заказ-нарядов в 1С при
сдаче/приёмке техники. Отчётность показывает, насколько активно инженеры пользуются планшетами вместо
ПК, динамику, синхронность работы дирекций и персональную эффективность сотрудников.

**Провайдер ИИ для направления:** DeepSeek Chat Completions (`AI/PROVIDER = DeepSeek`, модель `deepseek-chat`) —
заменяет Gemini, указанный в исходной постановке; выбран на этапе пилота как доступный напрямую из
внутреннего контура без обхода блокировок (см. Core §3).

## 2. Источник данных и формат обмена

Имя файла: `sppr_tablet_<дата>_<время>.json`. На каждый заказ-наряд 1С формирует несколько записей
истории статусов — заказ-наряд «расщепляется» на комбинации (ЗН × дирекция × статус).

```json
[
  {
    "number": "000300944",
    "date": "2025-10-24T15:06:39",
    "ready_for": "Готов к приёмке",
    "direction": "ДГМ",
    "status_date": "2025-10-26T13:50:25",
    "employee": "Барыкин Илья Игоревич",
    "arm": "ПК",
    "post": "ремзона стк",
    "day_status": 26, "month_status": 10, "year_status": 2025,
    "week_status": 43,
    "zn_type": "Внеплановый ремонт",
    "emp_dep": "ДГМ",
    "model_type": "Автотранспорт",
    "in_bounds": true,
    "defekt_type": null,
    "defect_desc": null
  }
]
```

**Формат сообщения об ошибке** (лист `Logs`): Дата | Тип записи | Действие | Источник | Результат.

## 3. Схема `tbDATA` направления МТО

Поля JSON (раздел 2) без изменений + вычисляемые поля:

| Поле | Логика расчёта | Реализация (Function Contract Core §5.1) |
|---|---|---|
| `postN` | Нормализация поста: если `post` содержит «стк» (без учёта регистра) → `«СТК»`; если содержит «прк» → `«ПРК»`; иначе `postN = post` без изменений | `fnNormalizeFields` |
| `Key` | `[number] & "\|" & Text.From([date]) & "\|" & [ready_for] & "\|" & [direction]` | `fnComputeKey` |
| `deltaHours` | См. п. 3.1 ниже | `fnComputeGroupMetrics` |

Эти три функции — единственное, что Core ожидает от направления по контракту из Core §5.1
(фиксированные имена и сигнатуры); их реализация ниже специфична МТО.

### 3.1 Реализация функций (Power Query M-код)

Рабочий код — в файлах проекта (не дублируется здесь во избежание рассинхрона):
`src/powerquery/fnNormalizeFields.pq`, `src/powerquery/fnComputeKey.pq`,
`src/powerquery/fnComputeGroupMetrics.pq`.

> Код иллюстративный (не прогонялся в самом Power Query редакторе) — при реализации проверить в
> редакторе запросов Excel и поправить типы (`type table`, доступ к столбцам через `Table.Column`
> при необходимости).

**Логика `deltaHours`:** группировка по `(number, direction)` → `tStart` = `status_date` записи
`«Готов к приёмке»`, `tEnd` = `status_date` записи `«Готов к выбытию»` → `deltaHours =
Duration.TotalHours(tEnd − tStart)`, присваивается **только строке `«Готов к выбытию»`**
(считаем, что длительность ремонта относится к инженеру, зафиксировавшему закрытие наряда) —
у строки `«Готов к приёмке»` поле остаётся `null`.

> ⚠️ Предположение: если в рамках одной дирекции на один `number` приходится больше двух статусных
> записей (не соответствует примеру из постановки), функция берёт `min(status_date)` среди записей
> «Готов к приёмке» и `max(status_date)` среди записей «Готов к выбытию». Если это не так —
> требуется уточнение у заказчика.

## 5. Определения аналитических блоков (1–9)

**Общий фильтр для всех блоков, если не указано иное:** `in_bounds = ИСТИНА`, `arm <> ""`.

### Блок 1 — Свод по неделям и постам (Отчёт №4)
Строки: `direction → arm`; столбцы: `week_status`; значения: `Count(Key)`.
Доп. строка «% планшет» = `Count(arm="ПЛАНШЕТ") / Count(arm∈{ПК,ПЛАНШЕТ})` по каждой неделе и дирекции.
Фильтр: `arm ∈ {ПК, ПЛАНШЕТ}`. Раскраска строки «% планшет» — палитра из раздела 9.
→ Прямое соответствие примеру сводной таблицы §5.1 постановки.

### Блок 2 — Количество ремонтов по постам ремзоны (Отчёт №3)
Строки: `direction → postN`; значения: `Count(Distinct number)` (уникальных заказ-нарядов, не строк).
Фильтр: базовый.

### Блок 3 — Общие показатели (KPI текущей недели/окна)
Разовые агрегаты верхнего уровня: всего ЗН обработано за окно `REPORT/WEEKS_WINDOW`, `% планшет` по
ДГМ и по ДЭНТ за текущую неделю, тренд к предыдущей неделе (Δ п.п.). Набор фиксируется в коде на
этапе пилота (не пересчитывается диалогом с ИИ при каждом запуске) — согласовывается с заказчиком один раз.

### Блок 4 — Динамика `% планшет` по дирекциям (по неделям)
Строки: `direction`; столбцы: `week_status`; значение: `% планшет`.
Источник для gauge-индикатора Слайда 3 и для промпта ИИ (`slide3_conclusions`).

### Блок 5 — Динамика `% планшет` по постам ремзоны (по неделям)
Строки: `postN`; столбцы: `week_status`; значение: `% планшет`.
Источник для Слайда 4 (вместе с Блоком 2) и промпта ИИ (`slide4_conclusions`).

### Блок 6 — Рейтинг инженеров (Отчёты №1 и №5)
Строки: `employee`; значения: `% планшет` (текущая неделя/окно), `Count(number)` обработанных нарядов,
`Average(deltaHours)` — средняя длительность ремонта по закрытым нарядам инженера.
Сортировка по убыванию `% планшет`.
**Вывод на слайд:** первые `TOPN` строк (по умолчанию 10, см. `Variable/REPORT/TOPN`) — «отличники»,
последние `TOPN` строк — «двоечники». `TOPN` вынесен в `Variable`, чтобы не хардкодить «10» в коде.

> ⚠️ Расхождение с кодом (см. `next-steps.md`, Приоритет 2): здесь "% планшет" описан как
> «текущая неделя/окно», а `Block6RankedTable` в `modContentMTO.bas` фактически считает его по всей
> истории `tbDATA` без ограничения по `week_status`. Требует решения — какое поведение верное.

### Блок 7 — Синхронность дирекций (Отчёт №2)
Сопоставление активности ДГМ и ДЭНТ по одним и тем же `number`/периодам: для каждого `number`,
присутствующего в обеих дирекциях, — разница между `status_date` записей `«Готов к выбытию»`
ДГМ и ДЭНТ (в часах). Агрегация: среднее по неделям.

### Блок 8 — Синхронность статусов (доп. разрез к Блоку 7)
То же сопоставление, но по неделям и постам одновременно — выявляет, в каких сочетаниях
пост/неделя рассинхрон между дирекциями наибольший.

### Блок 9 — Разбивка по видам ремонта/дефектов
Строки: `zn_type`; доп. срез — `defekt_type` (если заполнено); значения: `Count(number)`.
Источник для Слайда 5 (контекст к синхронности).

Реализация всех 9 блоков — в `src/vba/modContentMTO.bas`. Блоки 1, 4, 5, 9 строятся как PivotTable
(`BuildPivots()`, вызовы `modPivotBuilder.BuildPivotTable`, контракт Core §10, §16). Блоки 2, 3, 6, 7,
8 считаются напрямую по `tbDATA` через generic in-memory агрегатор Core `modAggregate.bas` (не Pivot —
классический PivotTable без Data Model не умеет Distinct Count, KPI за произвольное окно, сортировку
по вычисляемому значению и попарные разницы дат между строками). Статус реализации — см. §11.1
(закрыто) и `next-steps.md` (актуальный трекинг того, что уже проверено в реальном Excel).

## 7. Спецификация внешнего обогащения (DeepSeek API)

`POST https://api.deepseek.com/chat/completions`, модель `deepseek-chat`, таймаут 60 сек, без ретраев.

**Один комбинированный запрос** на все текстовые выводы (Слайды 3, 4, 5):

Системный промпт:
> «Ты ведущий аналитик данных. Проанализируй предоставленные агрегированные метрики использования
> планшетов в МТО (доля планшетов по дирекциям, ремзонам и синхронность). Сформируй краткие бизнес-выводы
> (до 4 предложений на каждый) для 3-х слайдов. Ищи аномалии. Не используй данные, которых нет во входном
> JSON. Ответ строго в формате JSON: `{"slide3_conclusions": "...", "slide4_conclusions": "...",
> "slide5_conclusions": "..."}`, без markdown-разметки вокруг JSON.»

Пользовательское сообщение — агрегаты Блоков 4, 5, 7, 8, 9 (по ДГМ и ДЭНТ), сериализованные в
компактный текст, **без ФИО** (Блок 6 в запрос не включается — см. раздел 8).

Разбор ответа — строковыми функциями по трём известным ключам; при обрезанном/невалидном ответе —
для нераспознанного слайда подставляется заглушка «Внешний ИИ недоступен, показатели см. в таблицах выше».

Реализация — `src/vba/modContentMTO.bas`: `BuildPrompt()` (сборка тела запроса; сериализует Блоки
4, 5 через `PivotToCompactJSON`, Блоки 7 и 8 — через `Block7ToCompactText()`/`Block8ToCompactText()`,
Блок 9 — через `PivotToCompactJSON`) и `ParseAIResponse(...)` (контракт Core, см. `modMain.bas`).

## 11. Чек-лист приёмки (МТО)

- [ ] Загрузка JSON 100 МБ/200k строк выполняется Power Query без зависания Excel.
- [ ] При повторной загрузке файла с изменёнными значениями по тем же `Key` — строки в `tbDATA`
      обновляются, а не дублируются и не остаются старыми (полный upsert, не только anti-join).
- [ ] `postN` нормализует «стк»/«прк» в любом регистре.
- [ ] Блоки 1–9 фильтруют `in_bounds=ИСТИНА`, исключают пустой `arm`.
- [ ] `deltaHours` рассчитан для всех `number`, где в рамках дирекции есть обе записи статуса,
      и присвоен строке `«Готов к выбытию»`.
- [ ] Блок 6 показывает ровно `Variable/REPORT/TOPN` (по умолчанию 10) строк в топе и антитопе.
- [ ] Строка «% планшет» раскрашена по палитре `#ef4444/#f59e0b/#10b981`.
- [ ] ФИО не уходят в запрос к DeepSeek ни в каком виде.
- [ ] При недоступности DeepSeek отчёт всё равно формируется и сохраняется в `result\`.
- [ ] Готовый `.html` открывается офлайн в Chrome без интернета.
- [ ] Ни один компонент не обращается к почтовым серверам или Google Диску.
- [ ] Файл `ReportMTO.xlsm` передаётся заместителю и работает у него без доп. настройки, кроме листа `Variable`.

## 11.1 Пробелы, вскрывшиеся при написании кода — статус: закрыто

Все пять пунктов реализованы в `src/vba/modContentMTO.bas` через новый generic-модуль Core
`src/vba/modAggregate.bas` (in-memory группировка/фильтрация по 2D-массиву, без Data Model):

- [x] **Блок 2** — честный `Distinct Count` по `number` через `modAggregate.GroupCountDistinct`,
      прокси-фильтр по `ready_for` больше не нужен.
- [x] **Блок 3 (KPI)** — реализован в `BuildBlock3KPI()`: всего ЗН за окно `WEEKS_WINDOW` (через
      `GroupCountDistinct` по неделям), `% планшет` ДГМ/ДЭНТ текущей недели и Δ к предыдущей.
      «Текущая неделя» определена как максимальный `week_status`, реально присутствующий в данных
      (не календарная неделя) — сознательное решение, чтобы KPI не расходился с данными при
      задержке выгрузки; при необходимости легко заменить на `DatePart("ww", Date)`.
- [x] **Блок 6 (топ/антитоп-`TOPN`)** — честная сортировка по `% планшет` через
      `modAggregate.SortDictionaryKeysByValue` (сортировка пузырьком, приемлемо для десятков-сотен
      сотрудников), `Average(deltaHours)` — через `modAggregate.GroupAverage`. См. ⚠️ в §5 —
      «текущая неделя/окно» из описания и «вся история» в коде пока расходятся.
- [x] **Блоки 7/8 (синхронность дирекций)** — реализована попарная разница `status_date` записей
      `«Готов к выбытию»` между ДГМ и ДЭНТ по одному `number` (`BuildSyncPairs()`), агрегация по
      неделям (Блок 7) и по неделям×постам (Блок 8). `postN` относится к заказ-наряду целиком
      (подтверждено), поэтому берётся из любой из двух строк без допущений — прежнее ⚠️ снято.
      Обе агрегации также сериализуются в промпт ИИ через `Block7ToCompactText`/`Block8ToCompactText`
      (см. §7 — ранее здесь была неверная пометка, что Блок 8 в промпт не попадает).
- [x] **«% планшет» в Блоках 1/4/5** — считается напрямую по `tbDATA` через `modAggregate.GroupCount`
      (не из уже построенного Pivot) и выводится отдельной раскрашенной строкой под таблицей
      (`PivotToHTMLTableWithPercent`).

Остаётся не автоматизированным (сознательно, вне контракта Core/Content Spec): `SYNC_THRESHOLD_MIN`
из `Variable` пока не используется в Блоках 7/8 — там выводится только среднее время расхождения,
а не доля нарядов, укладывающихся в порог. Если заказчику нужна именно доля/флаг «не синхронизировано» —
это независимое расширение `Block7ToCompactText`/`Block8ToCompactText`, а не пробел контракта.

## 12. Открытые вопросы / допущения (МТО-специфичные)

**В: Что если DeepSeek вернёт невалидный JSON (обрезан по лимиту токенов)?**
О: Строковый парсер мягко деградирует — для слайда без распознанного ключа подставляется заглушка,
остальные слайды используют полученный текст.

**В: Нужно ли версионировать файлы в `result\`?**
О: Да — имя файла включает дату/время (`Report_<YYYYMMDD_HHMMSS>.html`), старые отчёты не удаляются
автоматически; ротация — вне объёма пилота.

**В: `deltaHours` — если у наряда в дирекции больше двух статусных записей?**
О: См. допущение в §3.1 — берутся `min`/`max` по `status_date`; требует подтверждения заказчиком,
если такие случаи реально встречаются в данных 1С.

**В: Почему `TOPN` вынесен в `Variable`, а не зашит как 10?**
О: Чтобы будущие направления (по аналогии с МТО, см. Core §16) могли переиспользовать Блок 6
с другим размером топ-листа без изменения кода — только правкой листа `Variable`.
