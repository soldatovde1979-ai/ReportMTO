## Зачем

Чтобы на вопрос «что сейчас стоит в Excel» был ответ, который видно, а не
вычисляют сравнением файлов. Версия живёт **внутри книги**, в журнале версий и в
подвале каждого отчёта. Имя файла книги не меняется — ярлыки, «Последние
документы» и скрипты остаются рабочими.

## Одна команда

Из корня проекта, **книга должна быть закрыта**:

```
powershell -NoProfile -ExecutionPolicy Bypass -File install\install.ps1
```

Перед запуском впишите в `install\VERSION` ниже первой строки человеческое
описание изменений: **что** добавлено; **какая** ошибка исправлена (какая, а не
как исправлялась); **что** и с **каким результатом** оптимизировано. Описание
попадёт в `CHANGELOG.md` первым абзацем записи новой версии. В выводе `-DryRun`
это контролируется маркерами `DESC_FOUND` / `DESC_EMPTY`.

Что происходит по шагам:

1. считаются хеши исходников (`src\vba\*.bas`, `src\powerquery\*.pq`, `tmp_index.html`
   и документация `README.md`, `docs\**\*.md`, `install\*.md`) и сравниваются с
   прошлым релизом;
2. установка: бэкап в `bak\` -> VBA-модули -> запросы Power Query -> шаблон ->
   пост-верификация;
3. запускается `tools\compile_check.ps1` — принудительная компиляция VBA;
4. **только если оба шага вернули 0**: поднимается версия, в книгу пишутся ключи
   `BUILD/VERSION`, `BUILD/DATE`, `BUILD/SRC_MD5`, прогоняются недостающие миграции,
   добавляется запись в `CHANGELOG.md`.

Если установка или компиляция упали — версия **не меняется**, журнал не трогается.
Это и есть смысл правила «версия фиксируется только при нулевом коде возврата».

Только установка без версионирования (например, для build-книги):

```
powershell -NoProfile -ExecutionPolicy Bypass -File install\install.ps1 -Target ".\build" -InstallOnly
```

Посмотреть, что будет сделано, ничего не трогая:

```
powershell -NoProfile -ExecutionPolicy Bypass -File install\install.ps1 -DryRun
```

## Разбор команды и ключи

### Из чего состоит строка запуска

```
powershell -NoProfile -ExecutionPolicy Bypass -File install\install.ps1
```

| Часть | Что значит | Можно опустить |
|---|---|---|
| `powershell` | запуск Windows PowerShell 5.1 | нет |
| `-NoProfile` | не подгружать профиль PowerShell: он может переопределять функции и кодировку консоли, и скрипт поведёт себя иначе | можно, но не нужно |
| `-ExecutionPolicy Bypass` | разрешить выполнение этого скрипта. Действует только на текущий запуск, системную политику не меняет | нет: иначе Windows откажется запускать `.ps1` |
| `-File install\install.ps1` | что запускаем; путь считается от текущей папки — отсюда «из корня проекта» | нет |

Всё, что идёт после имени скрипта, — ключи самого скрипта.

### Ключи `install\install.ps1`

| Ключ | Зачем | По умолчанию |
|---|---|---|
| `-DryRun` | показать план релиза, ничего не меняя: ни книгу, ни версию, ни журнал | выключен |
| `-InstallOnly` | только установка + верификация, без версии/миграций/CHANGELOG | выключен |
| `-Bump patch\|minor\|major` | какой разряд версии поднять | `patch` |
| `-Target "<путь>"` | книга (релиз) или книга/папка (с `-InstallOnly` патчатся все `*.xlsm` папки) | `.\ReportMTO.xlsm` |
| `-Force` | поставить поверх более новой книги (осознанный откат), факт пишется в `CHANGELOG.md` | выключен |
| `-SkipCompile` | пропустить `compile_check.ps1` | выключен, пропускать не рекомендуется |
| `-ProjectRoot "<путь>"` | корень проекта, если скрипт запускают из другого места | папка над `install\` |

Ключи комбинируются:

```
powershell -NoProfile -ExecutionPolicy Bypass -File install\install.ps1 -Bump minor -DryRun
powershell -NoProfile -ExecutionPolicy Bypass -File install\install.ps1 -Target ".\build" -InstallOnly
```

### Ключи скриптов, которые вызываются внутри

Отдельно они нужны редко — `install.ps1` вызывает их сам.

| Скрипт | Ключи |
|---|---|
| `tools\compile_check.ps1` | `-Book` — книга, компиляция идёт на временной копии |

## Первый запуск

Механизм заводится с нуля, поэтому первый прогон ведёт себя не так, как обычный.

Что произойдёт:

- прошлого состояния нет (`install\release.state` ещё не создан) — в выводе будет
  `RELEASE_FIRST_RUN`, **версия не поднимается**: фиксируется 8.1.0 из `install\VERSION`
  как точка отсчёта;
- в книге нет ключа `BUILD/VERSION`, поэтому её версия считается `0.0.0` — применится
  миграция `8.1.0__variable_keys.ps1` и заведёт `DATA/KEEP_WEEKS = 52`;
- в `CHANGELOG.md` появится первая запись, в книге — `BUILD/VERSION = 8.1.0`.

Порядок действий:

1. Закрыть книгу.
2. Посмотреть план, ничего не меняя:
   `powershell -NoProfile -ExecutionPolicy Bypass -File install\install.ps1 -DryRun`
3. Если вывод разумный — тот же запуск без `-DryRun`. Успех выглядит как `RELEASE_OK 8.1.0`.
4. Открыть книгу, нажать «Сформировать отчёт», проверить подвал готового HTML: там
   должно появиться «сборка 8.1.0».

Если шаг установки или компиляции упадёт — версия, `release.state` и `CHANGELOG.md`
останутся нетронутыми, а книгу можно вернуть из `bak\` (установщик кладёт туда копию
до любых правок). Это ожидаемое поведение, а не половинчатое состояние.

## Какой номер получится

`МАЖОР.МИНОР.ПАТЧ` (SemVer).

| Что произошло | Команда | Результат |
|---|---|---|
| Правка внутри модулей, поведение то же | обычный запуск | патч: 8.1.0 → 8.1.1 |
| Новый блок, новая метрика, новый ключ Variable | `-Bump minor` | 8.1.1 → 8.2.0 |
| Сменился контракт: плейсхолдеры шаблона, схема tbDATA, состав листа Variable | `-Bump major` | 8.2.0 → 9.0.0 |
| Исходники не менялись, просто переустановка | обычный запуск | версия та же |

Как выбрать: спросить себя, **кто заметит разницу и надо ли ему что-то делать**.
Никто не заметит — патч. Заметит, но делать ничего не нужно — минор. Заметит и
придётся вмешаться руками (перезагрузить JSON, поправить шаблон, завести ключ),
иначе сломается — мажор. Сюда же относится изменение определения метрики, после
которого числа несопоставимы с прошлыми отчётами.

Патч считается сам. Минор и мажор — ваше осознанное решение, поэтому их
приходится назвать флагом; менять контракт молча всё равно нельзя.

```
powershell -NoProfile -ExecutionPolicy Bypass -File install\install.ps1 -Bump minor
```

## Где смотреть версию

| Где | Что видно |
|---|---|
| Лист `Variable` книги | `BUILD/VERSION`, `BUILD/DATE`, `BUILD/SRC_MD5` |
| Подвал любого отчёта в `result\` | «сборка 8.1.1» |
| `install\VERSION` | версия исходников (первая строка) и человеческое описание следующей версии |
| `CHANGELOG.md` | что менялось от версии к версии: сначала человеческое описание, затем техника |

`BUILD/SRC_MD5` отвечает на вопрос «книга совпадает с `src\` или разошлась»:
если после правки исходников хеш в книге прежний — в книгу их никто не ставил.

## Что лежит в install\

| Файл | Что это | Запускать напрямую | Правится руками |
|---|---|---|---|
| `install.ps1` | **Точка входа.** Установка И релиз: дайджест -> установка -> компиляция -> версия -> миграции -> журнал; `-InstallOnly` — только установка без версионирования | да, это ваша команда | редко |
| `install_prod.ps1` | Прод-обёртка: вызывает `install.ps1` против корневой `.\ReportMTO.xlsm` (по умолчанию) | да | редко |
| `VERSION` | Версия исходников: первая строка — номер (ведёт `install.ps1`), ниже — человеческое описание изменений | нет | только описание ниже первой строки |
| `release.state` | Служебный: хеши исходников прошлого релиза. Отвечает на вопрос «менялись ли исходники» | нет | **никогда** |
| `migrations\*.ps1` | Доп. код конкретной версии: то, что нужно доделать в книге сверх установки кода | нет, их вызывает `install.ps1` | да, при необходимости |
| `install-v7.1.md` | Историческая инструкция ручного обновления v7.0 -> v7.1 | — | — |

Рядом, вне папки: `CHANGELOG.md` в корне (накопительный журнал, ведёт `install.ps1`)
и `tools\compile_check.ps1` (компиляция VBA на временной копии).

Заменённое лежит в `tools\archive\`: `apply_v8.0.ps1`, `add_keep_weeks_key.ps1`
(ключ ретеншна — его заводит миграция `8.1.0__variable_keys.ps1`), а с 13.09.2026 —
`release.ps1` (объединён с `install.ps1` v2.0). `install_prod.ps1` возвращён в `install\`
14.09.2026 и снова в работе.

### Почему install и release были объединены

До 13.09.2026 установка и релиз жили в двух скриптах: `install.ps1` (механика) и
`release.ps1` (событие: версия + CHANGELOG + state). Практика показала, что
двухступенчатая цепочка вызовов затрудняла поиск места ошибки.

Теперь всё в одном `install.ps1`: полный цикл по умолчанию, `-InstallOnly` — для
тех, кому нужно только положить код в книгу без следа в версионировании. Прежнее
разделение операций сохранилось на уровне флага, а не отдельного файла.
`install_prod.ps1` остаётся отдельной обёрткой прод-установки: вызывает `install.ps1`
против корневой `.\ReportMTO.xlsm` (решение владельца от 14.09.2026).

## Миграции

Миграция нужна, когда новой версии мало установить код — надо что-то доделать в
книге: завести ключ на листе `Variable`, перестроить таблицу, почистить данные.

Имя файла: `install\migrations\<версия>__<короткое имя>.ps1`, например
`8.1.0__variable_keys.ps1`. Правила:

- миграция применяется, если её версия **больше** версии, записанной в книге;
- порядок — по возрастанию версии;
- строка `# requires-from: 8.0.0` в первых 20 строках означает «книгу ниже 8.0.0
  этой миграцией не обновлять»: релиз остановится и скажет, какую промежуточную
  версию поставить сначала;
- миграция получает открытую книгу и **не сохраняет и не закрывает** её — это
  делает `install.ps1`;
- миграция обязана быть идемпотентной: повторный прогон не должен ломать данные.

Заготовка:

```powershell
# 8.3.0__описание.ps1
# requires-from: 8.1.0
param($Workbook, [string]$BookPath)
$ErrorActionPreference = "Stop"

# ... работа с $Workbook ...
Write-Output "MIG ADD что-то сделано"
```

Файл сохранять в UTF-8 **с BOM**, иначе PowerShell 5.1 прочитает кириллицу как ANSI.

## Работа с двух компьютеров

В git лежат исходники, документы и скрипты. **Рабочей книги и выгрузок там нет**
(`ReportMTO.xlsm`, `data\*.json`, `*.key` — в `.gitignore`), поэтому книгу на второй
машине переносят отдельно или собирают заново из `build\ReportMTO_starter.xlsx`.

Версия живёт **в книге** (`BUILD/VERSION`), а состояние прошлого релиза — **в git**
(`install\release.state`). Отсюда правило:

1. `git pull` — перед релизом;
2. `install\install.ps1`;
3. `git push` — сразу после.

Релизить лучше с одной машины. Если всё-таки релизнули с двух, версии разойдутся:
две сборки с одним номером и разным содержимым.

### Защита от отката

Перед установкой `install.ps1` читает версию из книги и сравнивает её с
`install\VERSION`:

| Что увидел | Что делает |
|---|---|
| Книга старее исходников | Штатный апгрейд, применяются миграции по возрастанию |
| Книги без `BUILD/VERSION` | Считает её `0.0.0`, применяет все миграции |
| **Книга новее исходников** | `RELEASE_FAIL` — старый код поверх нового не ставится. Нужен `git pull` |
| Версии равны, `BUILD/SRC_MD5` разный | `BOOK_MD5_MISMATCH` — та же версия, другое содержимое: релиз делали с другой машины |

Осознанный откат (например, новая сборка оказалась негодной) — тот же запуск с
флагом `-Force`; факт отката попадает в `CHANGELOG.md` отдельной строкой:

```
powershell -NoProfile -ExecutionPolicy Bypass -File install\install.ps1 -Force
```

Цена проверки — одно открытие книги на чтение до установки, на 52 МБ около
полминуты. Это дешевле, чем молча откатить код и потом искать, почему в отчёте
пропал блок.

### Про Google Диск

Папка проекта лежит внутри синхронизируемого диска, то есть Диск синхронизирует и
саму `.git\`. Две системы синхронизации на один репозиторий рано или поздно ломают
его (зависший `.git\index.lock` уже ловили 11.09.2026). Выбирайте одно: либо git
через GitHub — и тогда папка не синхронизируется на обеих машинах сразу, либо
Диск — и тогда не коммитить со второй машины.

## Семантика DEBUG

Ключ `DEBUG` на листе `Variable` управляет логами (v8.2, 13.09.2026). Ключа нет -> `0`.

| DEBUG | Лист `Logs` книги | Внешний файл `ReportMTO.log` рядом с книгой |
|---|---|---|
| 0 | только «Веха» и «Ошибка» | не пишется |
| 1 | только «Веха» и «Ошибка» | только «Ошибка» и «Веха» |
| 2 | только «Веха» и «Ошибка» | полный лог: все типы записей, включая трассировку с таймингами |

Лист `Logs` всегда содержит только вехи («Строк до/после», «Записано N из M») и
ошибки. Полный текст при `DEBUG=2` смотрите в `ReportMTO.log`.

## Если что-то пошло не так

| Маркер в выводе | Что значит |
|---|---|
| `RELEASE_SOURCES_SAME` | исходники не менялись, версия не поднимается — это нормально |
| `DESC_FOUND` | описание для CHANGELOG прочитано из install\VERSION — штатно |
| `DESC_EMPTY` | описание не заполнено — запись в CHANGELOG пойдёт с плейсхолдером |
| `VERIFY_FAIL` | книга не совпала с исходниками, версия не записана; смотреть строки `*_VERIFY_FAIL` выше |
| `COMPILE_FAIL` | VBA не компилируется, версия не записана |
| `BOOK_ERROR` | модули поставлены, но версию/миграции в книгу записать не удалось |
| `MIG_SKIP` | миграция старше версии книги, применять нечего |
| `RELEASE_FAIL книга НОВЕЕ исходников` | на этой машине старый клон — `git pull`, либо `-Force` для осознанного отката |
| `BOOK_READ_WARN` | версию книги прочитать не удалось, проверка отката пропущена — установка идёт как раньше |
| `RELEASE_OK 8.1.1` | всё прошло, в книге версия 8.1.1 |

Резервная копия книги и шаблона делается установщиком в `bak\` до любых правок.

## Чего механизм не делает

- **не переименовывает книгу** — сознательно: имя файла как носитель версии ломает
  ярлыки и список «Последние», а на синхронизируемой папке каждое переименование
  это повторная заливка всей книги в облако;
- **не пишет версию, если установка не прошла** — при `VERIFY_FAIL` или
  `COMPILE_FAIL` `VERSION`, `release.state` и `CHANGELOG.md` остаются прежними;
- **не трогает данные** — `tbDATA`, кнопки и подключения Power Query установщик
  не меняет, миграции работают только с тем, что явно описано в них.
