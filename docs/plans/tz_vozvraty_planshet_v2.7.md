## 1. Откуда взялся «Отказ» — отвечаю, потому что вопрос справедливый

`Отказ` — **не поле выгрузки 1С**. Это одна из категорий классификатора «характер
работы», который строится в коде (`modContentZone.BuildRules`, `AddKind c, "Отказ", …`)
**по тексту поля `defect_desc`** — по списку ключевых слов. Рядом с ним такие же
придуманные категории: «Оформление документов», «Обслуживание», «Дефектовка и осмотр»,
«Изготовление и замена узла».

То есть фильтр «только отказы» означал «в описании дефекта нашлись слова из списка».
Список писал разработчик, в документации выгрузки его нет, проверить его точность
нечем. Неудивительно, что происхождение было непонятно.

Вид воздействия `zn_type` — наоборот, поле выгрузки. В примерах данных оно принимает
пять значений:

| Значение | Строк |
|---|---|
| **Внеплановый ремонт** | 344 |
| Omnicomm | 56 |
| ТО3 | 24 |
| ТО4 | 8 |
| ТО1 | 8 |

Отбор по нему проверяем, воспроизводим и не зависит от того, как механик написал
описание. Замена оправдана.

## 2. Задача 1. Фильтр «Отказ» → вид воздействия «Внеплановый ремонт»

**Правило:** везде, где сейчас стоит отбор `Z_KIND = "Отказ"` либо `Not IsPlanned(zn_type)`,
ставится точное сравнение `zn_type = "Внеплановый ремонт"`.

Значение выносится в константу с возможностью переопределить ключом `Variable`
(`REPORT/UNPLANNED_TYPE`): в другой выгрузке написание может отличаться, и тогда
правится ключ, а не код.

### 2.1 Где меняется

| Блок | Сейчас | Станет |
|---|---|---|
| Плитки возвратов | «Отказ» + `Not IsPlanned` | «Внеплановый ремонт» |
| Возвраты помесячно, понедельно, по узлам | то же | то же |
| Подозрение на повтор | `Not IsPlanned` | «Внеплановый ремонт» |
| Парето отказов | `Not IsPlanned` | «Внеплановый ремонт» |
| Детализация категории дефекта | `Not IsPlanned` | «Внеплановый ремонт» |
| Хроники парка | `Not IsPlanned` | «Внеплановый ремонт» |
| Отказы помесячно год к году | «Отказ» | «Внеплановый ремонт» |
| Износ по счётчику | «Отказ» | «Внеплановый ремонт» |
| Возвраты по подписи ДЭНТ (4 блока) | «Отказ» + `Not IsPlanned` | «Внеплановый ремонт» |

На текущих данных `Not IsPlanned` и «Внеплановый ремонт» дают почти одно и то же —
`IsPlanned` считает плановыми ТО\* и Omnicomm, а других значений в выгрузке нет.
Так что цифры по этим блокам почти не сдвинутся. Но отбор станет явным и управляемым,
а не выводимым из списка префиксов в коде.

Цифры **сдвинутся заметно** там, где стоял «Отказ»: туда попадали только наряды,
в описании которых нашлись нужные слова. Насколько именно — узнаем на прогоне.

### 2.2 Неочевидное следствие: уровни строгости схлопываются

Сейчас `RetPairs` считает возвраты на трёх уровнях:

| Уровень | Ключ совпадения | Дополнительный отбор |
|---|---|---|
| 0 | группа дефекта | — |
| 1 | группа + узел | — |
| 2 | группа + узел | **только «Отказ»** |

После замены отбор «только Отказ» уходит в общую базу, и **уровень 2 становится
равен уровню 1**. Плитки «по подкатегории» и «по отказу» начнут показывать одно и
то же число.

**Предлагаю** оставить два уровня ключа и убрать третий:

| Плитка | Ключ | Окно |
|---|---|---|
| Возвратов по подкатегории · 7 суток | группа + узел | 7 |
| Возвратов по подкатегории · 30 суток | группа + узел | 30 |
| По группе дефекта · 7 суток | группа | 7 |
| По группе дефекта · 30 суток | группа | 30 |
| Медиана интервала | — | 30 |

Пять плиток вместо пяти, но без дубля. Если считаете, что «по группе дефекта» вообще
лишнее — скажите, оставлю только подкатегорию, будет три плитки.

## 3. Задача 2. Два окна, 7 и 30, во всех блоках возвратов

**Правило:** там, где показывается число или доля возвратов, показываются **оба окна**.
Пока не решено, какое единственное верно, отчёт не выбирает за читателя.

### 3.1 Как это выглядит в каждом блоке

**Возвраты по подписи ДЭНТ** (итог и три разреза):

| Подпись ДЭНТ на выбытии | Нарядов | Вернулись ≤7 | Доля ≤7 | Вернулись ≤30 | Доля ≤30 |
|---|---|---|---|---|---|
| Есть, с планшета | | | | | |
| Нет подписи с планшета | | | | | |
| **Итого** | | | | | |

**Разрез по восьми неделям** — две группы × два окна × (нарядов, доля). Чтобы не
получить двенадцать строк, предлагаю в недельной таблице показывать **только доли**:
четыре строки (планшет ≤7, планшет ≤30, без планшета ≤7, без планшета ≤30) плюс две
строки «нарядов» на группу. Итого шесть.

**Два года по месяцам** — количество возвратов, как договорились. Два окна удваивают
строки: 2 года × 2 группы × 2 окна = восемь строк на двенадцать столбцов. Это уже
много. **Предлагаю** в этом блоке дать таблицу по окну 30 суток, а окно 7 — вторым
графиком под ней. Либо оставить один выбранный вами уровень. Нужно решение.

**Возвраты помесячно и понедельно** (существующие блоки слайда 6) — вторая линия
на том же графике: сейчас там столбики «отказов за период» и линия «доля возвратов».
Добавляется вторая линия — доля по окну 7. Потребуется правка примитива `RetChart`,
он рисует одну линию.

**Возвраты по узлам** — две колонки долей вместо одной.

### 3.2 Что нужно в коде

Сейчас признак «после этого наряда был возврат» (`mRetSrc`) наполняется **одним**
вызовом `RetPairs` с окном 30. Для двух окон нужны два словаря: `mRetSrc7` и
`mRetSrc30`, и два прохода вместо одного.

Проход по парам — самая дорогая часть расчёта возвратов. Второй проход её удваивает.
На текущих объёмах это терпимо, на 255 тыс. строк надо будет замерить.

### 3.3 Важно про соотношение окон

Возврат в окне 7 суток **всегда** входит и в окно 30: это вложенные множества.
Поэтому «доля ≤30» никогда не меньше «доли ≤7», а их разница — возвраты второй–
четвёртой недели. Это стоит написать в пояснении один раз, иначе читатель будет
пытаться их складывать.

## 6. Ответ на вопрос 7.1: цепочки возвратов и к какой дате относить

Уточнение владельца 17.09.2026: «если наряд открыт менее чем 7 или 30 дней от
последнего наряда (он может быть как первичным, так и уже возвратным) — возможно?»

### 6.1 Да, и это уже так работает

Проверено по коду `RetPairs`. Наряды машины по одному ключу дефекта сортируются по
дате, и **каждый по очереди становится базой**:

```vba
For i = 0 To UBound(ds) - 1          ' каждый наряд по очереди - база пары
    base = za(Z_CLOSED)              ' отсчёт от ЗАКРЫТИЯ базового наряда
    For j = i + 1 To UBound(ds)
        gp = Int(ds(j) - base)       ' ds(j) - дата СОЗДАНИЯ следующего наряда
        If gp > winDays Then Exit For
```

Значит цепочка А → Б → В даёт **два** возврата: пару (А, Б) на итерации `i = А` и
пару (Б, В) на итерации `i = Б`. Наряд Б одновременно возврат — для А, и источник
возврата — для В. Ровно то, что вы описали. Менять ничего не нужно.

Определение тоже совпадает с вашей формулировкой дословно: **следующий наряд создан
не позже чем через N дней после закрытия предыдущего**.

### 6.2 Две оговорки, которые стоит знать

**Если базовый наряд не закрыт**, отсчёт идёт от его создания (`If base <= 0# Then
base = za(Z_DATE)`). Это подмена: у незакрытого наряда «после ремонта» не наступило,
и окно считается от другой точки. Наряды, закрытые позже, в блоках возвратов по
подписи и так отсекаются условием «окно истекло», но в существующих блоках слайда 6
такие пары засчитываются. Стоит решить отдельно — оставить или исключать незакрытые
из базы.

**Считается только ближайший возврат** в окне (`Exit For` после первой подходящей
пары). Если после закрытия А в окне пришли и Б, и В, пара будет только (А, Б).
Это сделано намеренно, комментарий в коде: иначе хроническая машина утраивает долю.
Цепочку это не ломает — (Б, В) посчитается отдельно, если В попадает в окно от
закрытия Б.

### 6.3 Про какую дату спрашивал я — вопрос остаётся

Ваше уточнение задаёт **определение возврата**, и оно уже реализовано. Мой вопрос
7.1 был про другое: в недельной и месячной таблице **к какому периоду относить саму
пару**, у неё две даты.

| Вариант | Что означает | Когда виден |
|---|---|---|
| По **первому** наряду (как сейчас) | «качество ремонтов, сделанных в эту неделю» | только через 30 суток: пока окно не истекло, число неполное |
| По **второму** наряду (возвратному) | «сколько машин вернулось в эту неделю» | сразу, на следующий же день |

Разные вопросы, оба законные. Первый отвечает «как мы чинили тогда», второй —
«что происходит сейчас».

**С учётом вашей формулировки предлагаю второй вариант** — по дате открытия
возвратного наряда. Вы описали возврат как событие («наряд открыт менее чем через
N дней»), а событие естественно относить к моменту, когда оно случилось. Плюс
исчезает проблема пустого правого края таблицы из п. 4.2 постановки v2.0: относить
к неделе возврата можно сразу, ничего отсекать не нужно.

**Но** тогда числа разойдутся с существующими блоками «возвраты помесячно» и
«возвраты понедельно» на слайде 6 — они построены по первому наряду. Варианты:
перевести и их на дату возврата (тогда весь слайд единообразен), либо оставить и
написать в пояснениях, что блоки отвечают на разные вопросы.

**Предлагаю перевести все на дату возврата.** Нужно ваше слово: это сдвинет числа
в трёх существующих блоках.

## 7. Решение владельца 17.09.2026: два окна — две колонки слайда

> «4.2 — две таблицы, 7 и 30 дней, будем мириться с пустотой. Можно на слайде так
> организовать, что слева отчёты по возвратам за 7 дней, справа 30».

Принято. Это снимает сразу три открытых вопроса и упрощает реализацию.

### 7.1 Как это меняет постановку

**Было** (мои предложения, отменяются):

- п. 3.1 — добавлять по два столбца «≤7» и «≤30» внутрь каждой таблицы;
- п. 4.2 v2.0 — сдвигать недельное окно на недели 12–5, чтобы не было пустого края;
- п. 5.2 — в блоке «два года» давать таблицу по 30 суткам, а 7 — отдельным графиком.

**Стало:** каждый блок возвратов существует в **двух экземплярах** — окно 7 и окно 30, —
и они стоят рядом в двухколоночной секции. Левая колонка везде 7 суток, правая везде 30.
Столбцы внутри таблиц не удваиваются, строки не удваиваются, читатель сравнивает
колонки взглядом.

Пустой правый край недельной таблицы остаётся и принят сознательно: в колонке
«30 суток» последние четыре недели будут пустыми, в колонке «7 суток» — одна.
Это честнее, чем сдвигать окно и подписывать его «последние 8 недель».

### 7.2 Раскладка слайда 6

Каждая пара — одна секция `.two-col`, заголовок колонки несёт окно:

| Секция | Слева | Справа |
|---|---|---|
| Итог по подписи ДЭНТ | окно 7 суток | окно 30 суток |
| По восьми неделям | окно 7 | окно 30 |
| Два года по месяцам | окно 7 | окно 30 |
| По возрасту техники | окно 7 | окно 30 |
| По группе техники | окно 7 | окно 30 |
| По группе дефекта | окно 7 | окно 30 |

Окно указывается и в подписи периода над блоком, и в заголовке колонки — чтобы при
печати на бумаге, где колонки могут разъехаться, было видно, что где.

### 7.3 Что это значит для кода

Построители получают параметр окна: `BuildRetArm(winDays)`, `BuildRetArmCut(cut, winDays)`
и так далее. Один и тот же код вызывается дважды с разными аргументами — отдельных
функций под каждое окно не будет.

Нужны два словаря признака возврата: `mRetSrc7` и `mRetSrc30`, то есть два прохода
по парам вместо одного. Это остаётся самой дорогой частью и на больших объёмах
потребует замера.

Плейсхолдеров становится вдвое больше: не шесть, а двенадцать.

### 7.4 Существующие блоки слайда 6

«Возвраты помесячно» и «Возвраты понедельно» построены на одном окне (30) и рисуют
одну линию. По тому же принципу их надо развести в две колонки — тогда правка
примитива `RetChart` (вопрос 5.3) **не нужна**: каждая колонка рисует свою линию
своим вызовом. Ещё одно упрощение от вашего решения.

## 8. Виртуальное поле «завершён для возвратов»

> Владелец 17.09.2026: «он может быть не закрыт только если ожидание ТМЦ или отменён,
> требует повторного планирования. Я бы условно для этой задачи считал, что эти два
> статуса — это статусы, которые наряд закрывают. Т.е. ещё одно поле виртуальное,
> `ZakritForVozvrat = isZakrit or status in (…)`».

Идея верная и решает проблему из п. 6.2. Но посылка про «только эти два статуса»
данными не подтверждается — проверил, и это меняет формулу.

### 8.1 Что в данных

Свёрнуто по нарядам из двух файлов `examples/` (55 нарядов, 440 строк):

| TekStatusPoDoc у наряда **без** `zn_closed` | Нарядов |
|---|---|
| Готов к приемке | 8 |
| В ремонте | 7 |
| Ожидается подача техники | 4 |
| Работы завершены | 3 |
| Отменен, требует повторного планирования | 2 |
| Готов к выбытию | 1 |

Все 30 закрытых нарядов имеют статус «Закрыт». «Ожидание ТМЦ» в этих примерах не
встретилось вовсе.

**Вывод:** незакрытыми бывают и наряды, которые просто ещё в работе — «В ремонте»,
«Готов к приемке», «Ожидается подача техники». Это нормальный ход процесса, а не
аномалия. Таких 19 из 25 незакрытых.

**Оговорка о надёжности:** 55 нарядов — крошечная выборка, два файла по 220 записей.
На полной выгрузке распределение может отличаться, и «Ожидание ТМЦ» наверняка есть.
Но сам факт, что незакрытые наряды бывают в работе, от размера выборки не зависит.

### 8.2 Почему это важнее, чем кажется

Сейчас в `RetPairs` у наряда без `zn_closed` окно отсчитывается **от даты создания**.
Значит наряд, который прямо сейчас стоит «В ремонте», уже участвует в расчёте как
база пары: машина из ремзоны не выходила, а «возврат» ей уже могут засчитать.

Это не теоретическая придирка: 19 нарядов из 55 в примерах — в работе.

### 8.3 Предлагаемое определение

Два поля, а не одно:

```
ZakritForVozvrat = (zn_closed > 0)
                   OR (TekStatusPoDoc = "Ожидание ТМЦ")
                   OR (TekStatusPoDoc = "Отменен, требует повторного планирования")

DataZavershenia  = zn_closed, если он есть
                   иначе — максимальная дата статуса по наряду
```

Второе поле необходимо: у наряда, завершённого по статусу, `zn_closed` пуст, а окно
возврата от чего-то отсчитывать надо. Дата создания не годится — это начало ремонта,
а не его конец. Ближайшее к «работа по наряду прекращена» — момент, когда наряд встал
в последний статус, то есть максимальный `status_date` по наряду.

Такого поля в снимке `mZn` сейчас нет: там хранятся только даты четырёх подписей.
Добавляется одно поле, заполняется в существующем проходе.

**Наряды, не прошедшие `ZakritForVozvrat`, из базы возвратов исключаются полностью.**
Сегодня они в неё попадают. Это изменит числа во всех блоках возвратов — и, судя по
примерам, заметно.

### 8.4 Побочный эффект, который стоит отметить

Те же два статуса уже выделены на слайде 1 в блоке «Наряды, которые не двигаются ни
к закрытию, ни к отмене» (`{{BLOCK_HANG_STATUS_SPECIAL}}`). Там они трактуются как
**застрявшие**, здесь — как **завершённые**. Противоречия нет: на слайде 1 вопрос
«почему работа встала», здесь — «можно ли считать, что машина уехала». Но трактовки
разные, и это стоит написать в пояснении обоих блоков, иначе читатель споткнётся.

## 9. Решение: пара относится к дате возвратного наряда

> Владелец 17.09.2026: «к возвратному („сколько вернулось на этой неделе“)».

Вопрос 7.1 / 8.10 закрыт. Неделя и месяц пары определяются по дате создания
**второго, возвратного** наряда. Метрика отвечает на вопрос «сколько машин вернулось
в этот период», а не «как мы чинили тогда».

### 9.1 Что меняется в существующих блоках

Счётчики `RetPairs` сейчас ведутся по периоду **первого** наряда:

```vba
If Not numM Is Nothing Then AddCnt numM, CStr(za(Z_MONTH)), 1#   ' za = первый наряд
If Not numW Is Nothing Then AddCnt numW, CStr(za(Z_WEEK)), 1#
```

Меняется на период второго наряда пары. Затрагивает три существующих блока слайда 6:
«Возвраты помесячно», «Возвраты понедельно» и недельную плитку слайда 1 «Возвратов
(7 дн.)» через `mRetNumW7`.

**Числа в них сдвинутся** — не из-за ошибки, а потому что метрика стала отвечать на
другой вопрос. Сдвиг заметен на границах периодов: возврат, случившийся в понедельник,
раньше засчитывался в неделю месячной давности.

Перевожу все на дату возврата: две трактовки на одном слайде хуже, чем сдвиг чисел.

### 9.2 Что это даёт даром

Проблема пустого правого края недельной таблицы (п. 4.2) **исчезает для новых блоков**:
возврат виден в ту же неделю, когда случился, отсекать нечего.

Отсечение по незакрытому окну остаётся нужным **только там, где считается доля** —
то есть в блоках «возвраты по подписи ДЭНТ»: знаменатель там наряды-базы, и у свежих
баз окно ещё не истекло. Для блоков, где считается просто количество возвратов
(помесячно, понедельно, два года), отсечение не требуется вовсе.

Это упрощает реализацию: в блоках количеств — никаких границ и оговорок.

## 10. Решение: дата завершения — от последнего статуса документа, для всех нарядов

> Владелец 17.09.2026: «предлагаю универсальное решение — от даты статуса документа,
> т.е. от последнего статуса, тогда и те два воздействия попадут автоматом под это
> правило».

Принято. Правило простое и общее:

```
DataZavershenia = максимальный status_date по наряду
```

Для всех нарядов без исключения. Виртуальное поле `ZakritForVozvrat` из раздела 8
**отменяется** — оно больше не нужно: «Ожидание ТМЦ» и «Отменен» попадают под общее
правило сами, никакого списка статусов вести не надо.

Окно возврата отсчитывается от этой даты. `zn_closed` в расчёте возвратов больше
не участвует.

### 10.1 Почему это лучше прежнего

| | Было | Стало |
|---|---|---|
| Закрытый наряд | от `zn_closed` | от даты статуса «Закрыт» — практически та же дата |
| «Ожидание ТМЦ», «Отменен» | от даты **создания** (подмена) | от даты последнего статуса |
| Наряд в работе | от даты **создания** (подмена) | от даты последнего статуса |
| Список статусов в коде | нужен | не нужен |

Подмена точки отсчёта, о которой шла речь в п. 6.2, исчезает целиком. Никаких
исключений и списков.

### 10.2 Риск, который остаётся, и как его проверить

Наряд, который прямо сейчас стоит «В ремонте» месяц, получит дату завершения
месячной давности и войдёт в базу как источник возврата. Машина при этом из ремзоны
не выходила.

Владелец на это ответил: незакрытые наряды разбираются отдельно, как ошибки учёта
(слайд 7, «хвост незакрытого»). Принято.

Но проверить стоит: в блоках по подписи ДЭНТ такой наряд попадёт в знаменатель и
занизит долю возвратов. Предлагаю на первом прогоне посмотреть, сколько в базе
нарядов, у которых последний статус — «В ремонте», «Готов к приемке» или «Ожидается
подача техники». Если их доля заметна, вернёмся к вопросу; если единицы — правило
работает как задумано.

### 10.3 Что нужно в коде

Одно новое поле снимка: `Z_LASTST` — максимальный `status_date` по наряду.
Заполняется в существующем проходе `EnsureZn`, где `status_date` уже читается.

В `RetPairs` строка

```vba
base = CDbl(za(Z_CLOSED))
If base <= 0# Then base = CDbl(za(Z_DATE))
```

заменяется на `base = CDbl(za(Z_LASTST))`.

## 11. Решение: медиана — только в разрезе вида воздействия

> Владелец 17.09.2026: «медиану разумно рассматривать только в разрезе вида
> воздействия, потому что ТО1 и ТО5 — это несовместимые вещи. Плитки пока оставим,
> а вот отчёты всё же надо распределять по виду воздействия».

Возражений нет: смешивать в одной медиане ТО1 и внеплановый ремонт — то же самое,
что усреднять замену лампочки с капремонтом двигателя.

### 11.1 Где сейчас медианы

| Блок | Медиана чего | Разрез по виду воздействия |
|---|---|---|
| «Вид воздействия: поток и застрявшее», слайд 1 | срок наряда «создание → закрытие» | **есть** — это и есть разрез |
| Плитка «Медиана в ремзоне», слайд 1 | срок наряда | нет |
| Плитка «Медиана интервала», возвраты | интервал до возврата | нет |
| «Сутки в ремзоне», фазы, слайд 7 | три фазы наряда по неделям | нет |
| Разбор средней фазы на возвраты | фаза «ремзона» | нет |
| «Парк и заезды», плитка | возраст парка | не применимо |
| «Сколько наряд живёт после подписи выбытия» | выбытие → закрытие | нет |
| «Создание → приёмка по видам техники» | постановка | по видам **техники**, не воздействия |
| «Простой против часов» | простой по машинам | нет |
| Гистограмма «приёмка → выбытие» | интервал | нет (блок не выводится) |

### 11.2 Что предлагаю сделать

**Плитки не трогаем** — так вы и сказали. Они дают одно число «в среднем по больнице»,
и это принято как обзорный показатель.

**Блоки с медианами переводим в разрез по виду воздействия.** Приоритет — по тому,
насколько сильно смешение искажает:

1. **«Сутки в ремзоне» (фазы)** — самый искажённый: ТО1 и внеплановый ремонт имеют
   принципиально разную длительность всех трёх фаз, а сейчас они в одной медиане.
   Предлагаю строки таблицы = виды воздействия, колонки = три фазы.
2. **Разбор средней фазы на возвраты** — там уже две группы, добавится третье
   измерение. Предлагаю ограничиться внеплановым ремонтом: возвраты и так считаются
   только по нему, а ТО в этот блок не попадает по определению.
3. **«Сколько наряд живёт после подписи выбытия»** — разрез по виду воздействия.
4. **«Простой против часов»** — там единица машина, а не наряд; разрез по виду
   воздействия не ложится. Предлагаю оставить.

### 11.3 Вопрос по объёму

Требование «отчёты распределять по виду воздействия» шире медиан: его можно понять
и как «все таблицы давать в разрезе `zn_type`». Это переделка почти всего отчёта.

**Уточните область:** только блоки с медианами (пункты 1–3 выше) или все блоки,
где сейчас считается что-то усреднённое по всем видам сразу.

## 12. Даты статуса документа в выгрузке нет — решение раздела 10 требует поправки

> Владелец 17.09.2026: «а его не выгружаю походу».

Проверено по `examples/` (440 строк). Полный список полей выгрузки не содержит даты
статуса документа. Что есть рядом:

| Поле | Заполнено | Что это |
|---|---|---|
| `TekStatusPoDoc` | 440 / 440 | текущий статус документа — **без даты** |
| `status_date` | 272 / 440 | дата события **подписания** (`ready_for` + `direction`) |
| `zn_closed` | 120 / 440 | дата закрытия наряда |
| `date` | 440 / 440 | дата создания наряда |

`status_date` — это не «когда документ встал в текущий статус», а «когда поставили
подпись». У 168 строк из 440 она пуста — это события «НЕ ПОДПИСАНО».

Значит буквально реализовать «от последнего статуса документа» **нельзя**: поля нет.

### 12.1 Что можно сделать сейчас, без правки выгрузки

Ближайшее доступное приближение — **максимальная `status_date` по наряду**, то есть
дата последней подписи. Для наряда, который реально прошёл ремзону, это и есть момент,
когда работа по нему закончилась.

Цепочка отсчёта:

```
DataZavershenia = max(status_date по наряду)     — если есть хоть одна подпись
                  иначе zn_closed                — если наряд закрыт без подписей
                  иначе наряд НЕ МОЖЕТ быть базой пары
```

Последняя строка принципиальна. Если у наряда нет ни одной подписи и нет даты
закрытия, мы **не знаем**, когда он завершился, и отсчитывать окно возврата не от
чего. Подставлять дату создания — это та самая подмена, от которой мы уходим.
Такие наряды из базы возвратов исключаются, и их число выводится строкой.

### 12.2 Что для этого правильно попросить у 1С

Настоящее решение — поле с датой текущего статуса документа в `export2mto.bsl`.
Тогда правило «от последнего статуса» станет буквальным, и заодно закроется ещё
два ограничения, уже записанных в отчёте:

- помесячный остаток по «нерабочим» статусам на слайде 1 считает наряды, которые
  числятся в статусе **сейчас**, а не тогда — потому что истории статусов нет;
- фазу «ремзона» нельзя разложить на очередь и ожидание ТМЦ по той же причине.

Полноценно это решает **история смены статусов**, а не одна дата. Но одна дата уже
снимает проблему отсчёта окна.

### 12.3 Заодно: два поля выгрузки не используются вовсе

При проверке всплыло. В выгрузке есть `Sektor` (сектор аэропорта, 5 значений, стабилен
внутри машины) и `ts` (представление машины: номер + группа + модель). Оба описаны
в `docs/data.md`, но **в коде не используются ни разу**.

`Sektor` — готовый организационный разрез, которого в отчёте нет: возвраты и простои
по секторам аэропорта могут показать то, чего не видно по ремзонам.

### 12.4 И предупреждение по блоку наработки

В этих же примерах `odometer` и `engine_hours` пусты **во всех 440 строках**.
По `docs/data.md` они заполнены у 41 % и 60 % строк — значит в примерах лежит другая
выгрузка. Блок «износ по счётчику» на таких данных построится пустым.

Проверить на реальной выгрузке обязательно, прежде чем считать блок рабочим.
