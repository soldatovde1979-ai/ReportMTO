# Анализ архитектора: пакетная загрузка длится >30 минут (эскалация по регламенту п.10)

> Версия: v1.0 от 13.09.2026. Основание: регламент ТЗ v1.0, задача 10 —
> «загрузка >30 минут -> анализ логов -> логи не дают ответа -> сообщить архитектору ->
> архитектор возвращается к п.1 (усиление логирования)».

## 1. Факты прогона

| Параметр | Значение |
|---|---|
| Книга | `ReportMTO.xlsm` (корень), релиз 8.1.4, `VERIFY_OK` + `COMPILE_OK` |
| Строк в `tbDATA` до загрузки | 255 148 |
| Файлов в очереди | 5 (75644 + 60924 + 58672 + 17552 + 4976 = **217 768 записей**) |
| `DEBUG` | 2 (установлен перед загрузкой) |
| Старт | 11:12:25 |
| Последняя запись лога | 11:12:26 «До Refresh» |
| Длительность на момент анализа | **> 41 минуты**, новых записей нет |

Что лог **подтвердил** (правки ТЗ v1.0 работают):

- манифест очереди пишется до загрузки, все 5 файлов распознаны;
- **сортировка по дате/времени из имени файла работает корректно**: 20260101_091948 →
  20260908_113800 → 20260908_113859 → 20260908_113928 → 20260910_211120;
- `rec`-счётчики извлечены из имён верно;
- запись «Веха» попала и в лист, и в файл; трассировка `DEBUG=2` пишется.

Что лог **не смог** показать: что происходит внутри `RefreshImportQuery`. Это
архитектурная граница, названная в ТЗ (п.2.3): при одном синхронном `Refresh` VBA не
видит ни строк, ни шагов M-кода. Логирование п.1 исчерпало свои возможности —
следовательно, эскалация обоснована, и решение лежит **не в VBA-логах**, а в
измерении самого конвейера Power Query.

## 2. Первопричина (Root Cause): стоимость конвейера на 217 тыс. записей

Все 41+ минут проходят внутри одного шага `modPQSync.RefreshImportQuery`.
Разбор [`Query-ImportJSON.pq`](../src/powerquery/Query-ImportJSON.pq:1) и вызываемых функций
даёт **пять независимых источников стоимости**, каждый из которых на 217 тыс. строк
измеряется минутами:

### 2.1. Пятикратная материализация набора в памяти

| Где | Что буферизуется |
|---|---|
| `Source` | `List.Buffer` — 217 768 записей JSON |
| `fnDedupByKey` | `Table.Buffer` перед `Table.Distinct` |
| `fnComputeGroupMetrics` | `Table.Buffer(tbl)` + `Table.Buffer(Lookup)` |
| `NewData` | `Table.Buffer(WithGroups)` |
| `UpsertedBuf` | `Table.Buffer(Upserted)` |

Итог: набор 217 тыс. строк × ~20 колонок удерживается в памяти одновременно в
нескольких представлениях. Это гигабайты и активный своп — типовая причина, когда
процесс «жив, но не двигается».

**Важно:** добавленный по ТЗ `List.Buffer` (п.3.1) сам по себе не дефект — он убирает
повторное чтение папки. Но в сумме с четырьмя унаследованными `Table.Buffer` общий
объём удержания стал критическим.

### 2.2. `fnComputeGroupMetrics` — `Table.SelectRows` внутри `Table.Group`

[`fnComputeGroupMetrics.pq`](../src/powerquery/fnComputeGroupMetrics.pq:37): на каждую
группу `(number, direction)` выполняются **два** `Table.SelectRows` по подтаблице.
При ~35–40 тыс. групп это десятки тысяч вложенных сканирований. Комментарий G-2
утверждает, что шаг оптимизирован, но оптимизация убрала только `{"GroupRows", each _}`;
построчная фильтрация внутри агрегата осталась.

### 2.3. Ретеншн — до шести `try/otherwise` на строку

[`Query-ImportJSON.pq`](../src/powerquery/Query-ImportJSON.pq:144) `ToDT` вызывается из
`RowAnchor` дважды на строку, и каждый вызов может пройти цепочку
`try DateTime.From → try ru-RU → try en-US → null`. На 217 тыс. строк это до
**1,3 млн блоков обработки исключений** — в M это одна из самых дорогих конструкций.

Причём в режиме папки эта защита **избыточна**: все строки новые и уже типизированы в
`fnNormalizeFields`. Терпимое приведение нужно только для строк, пришедших обратно с
листа через `qExistingData` (режим одного файла + upsert).

### 2.4. `fnComputeKey` — `try/otherwise` на каждую строку

[`fnComputeKey.pq`](../src/powerquery/fnComputeKey.pq:67): `try DateTime.ToText(...)
otherwise Text.From(v)` вызывается для каждой из 217 тыс. строк. Совместимость с
Office LTSC можно определить **один раз** на весь набор, а не на строку.

### 2.5. Выгрузка результата на лист

217 тыс. строк × ~20 колонок пишутся в `tbDATA` через QueryTable. Это минуты даже при
идеальном M-коде, и это неустранимая часть.

## 3. Почему это не поймали раньше

Прошлый успешный прогон (12.09.2026) шёл на том же объёме, но:

- ретеншн `KEEP_WEEKS=52` мог отсекать больше строк на прежнем составе данных;
- `tbDATA` содержала 255 148 строк — при повторной загрузке очистка выполняется, но
  Excel удерживает освобождённую память до конца сессии, и пиковое потребление выше.

Однозначного ответа сейчас нет — и это главный вывод: **измерений нет, есть только
гипотезы**. Поэтому первый шаг — не оптимизация вслепую, а профилирование.

## 4. Возврат к п.1: чем усилить логирование (задачи разработчику)

### Задача A. Профилирование конвейера (даёт точное «где», без гадания)

Power Query не предоставляет построчной трассировки, но позволяет **измерить префиксы
конвейера**. Создать диагностические запросы, каждый из которых обрывает конвейер на
своём шаге и возвращает только `Table.RowCount`:

| Запрос | Обрывается на шаге | Что измеряет |
|---|---|---|
| `qProf1_Source` | `Source` | чтение и парсинг 5 файлов JSON |
| `qProf2_Expanded` | `Expanded` | разворачивание записей в таблицу |
| `qProf3_Normalized` | `Normalized` | `fnNormalizeFields` |
| `qProf4_Key` | `WithKey` | `fnComputeKey` |
| `qProf5_Dedup` | `Deduped` | `fnDedupByKey` (сортировка + Distinct) |
| `qProf6_Groups` | `WithGroups` | `fnComputeGroupMetrics` |
| `qProf7_Retention` | `Retained` | ретеншн |

Новый VBA-макрос `modMain.ProfileImport` (или `tools\_tmp_profile_pq.ps1`) прогоняет их
по очереди с `Timer` и пишет в `ReportMTO.log` вехи вида
`ЭТАП qProf3_Normalized: 217768 строк, 412.5 c`. Разница между соседними этапами и есть
стоимость конкретной функции.

**Это и есть выполнение требования «пусть тормозит, зато найдём место»** — в форме,
которую Power Query физически позволяет.

### Задача B. Индикация живости во время Refresh

Добавить в `LoadPackage` перед `Refresh` включение `Application.StatusBar` и вехи с
интервалом — невозможно (VBA заблокирован синхронным Refresh). Альтернатива, которая
работает: **писать веху «Refresh начат, ожидаемое время при N записей — M минут»** с
оценкой по последнему успешному замеру (хранить в `Variable`, ключ
`DATA/LAST_LOAD_SECONDS`). Тогда владелец видит не тишину, а прогноз.

### Задача C. Устранение первопричины (после профилирования, по его результатам)

Правки делать **только по данным замеров задачи A**, в порядке убывания стоимости:

1. **Ретеншн без `try` в режиме папки**: если `IsFolder = true`, все строки типизированы —
   использовать прямое сравнение `datetime` без `ToDT`/`RowAnchor`; терпимую ветку
   оставить только для режима одного файла.
2. **`fnComputeGroupMetrics` одним проходом**: добавить колонки `__isStart`/`__isEnd`
   и `__t` ДО группировки, затем агрегировать `List.Min`/`List.Max` по колонке — движок
   стримит и не сканирует подтаблицы.
3. **`fnComputeKey` без построчного `try`**: определить поддержку формата один раз
   (проба на первой строке) и передать флаг.
4. **Ревизия буферов**: оставить `List.Buffer` в `Source` (нужен) и один `Table.Buffer`
   перед выгрузкой; убрать промежуточные, перепроверив детерминизм `Table.Distinct`.
5. **Режим папки минует `fnUpsert`**: при `IsFolder = true` и пустой `tbDATA` ветка уже
   возвращает `NewData` — убедиться, что `qExistingData` при этом вообще не вычисляется.

## 5. Что сделать владельцу прямо сейчас

1. **Не прерывать текущий прогон**, если Excel отвечает: процесс, вероятно, работает
   (запись на лист — последняя и самая долгая фаза). Признак живости — рост CPU у
   `EXCEL.EXE` и увеличение файла книги.
2. Если прогон завершится — зафиксировать «Записано N из M» и общее время: это станет
   базовой точкой отсчёта для задачи B.
3. Если прогон придётся прервать — выполнить задачу A (профилирование) на **одном**
   файле `sppr_tablet_20260910_211120_4976rec.json` (4976 записей), затем на двух, и
   экстраполировать: так виновник находится за минуты, а не за часы.

## 6. Честная оценка принятых ранее решений

- Правка `List.Buffer` (ТЗ п.3.1) **корректна** и устраняет повторное чтение папки, но
  её эффект перекрыт унаследованными буферами — это было видно только на реальном объёме.
- Граница логирования, названная в ТЗ п.2.3 («строки внутри PQ VBA не видит»),
  **подтвердилась на практике**: лог дал точку входа и исключил VBA-слой из подозрений,
  но место внутри M-кода без профилирования не определяется.
- Регламент п.10 **сработал штатно**: порог 30 минут поймал ситуацию, анализ логов
  выполнен, эскалация проведена, возврат к п.1 оформлен этим документом.
