## 0. Сначала о том, почему «выбытие с планшета так и не увидел»

Блок «Приёмка против выдачи · чем подписывают» (`{{BLOCK_ACCLEV_DENT}}` /
`{{BLOCK_ACCLEV_DGM}}`) написан и лежит в ветке — он показывает ПЛАНШЕТ, ПК и
% планшета **раздельно по приёмке и выдаче**, по восьми неделям, с итогом.

Увидеть его в отчёте пока нельзя по простой причине: **отчёт не пересобирался**.
Я правлю исходники `src\vba\*.bas` и `tmp_index.html`, а HTML рождается только
когда книга прогоняет `GenerateReport` или `DebugGenerateOffline` в Excel.
Excel в моём окружении нет. Тот отчёт, что у вас открыт, собран старым кодом.

Чтобы увидеть: забрать ветку, поставить код в книгу (`install\install.ps1 -Target build
-InstallOnly`), прогнать `DebugGenerateOffline`. Пока этого не сделано, **все** правки
последних двух дней существуют только в виде текста.

## 1. Зачем это нужно: гипотеза, которую проверяем

Весь отчёт держится на одном допущении, которое пока нигде не проверено:
**дисциплина подписания влияет на результат ремонта**.

Пока части живут отдельно. Слайды 2–3 говорят «столько-то процентов подписей с
планшета». Слайд 6 говорит «столько-то процентов возвратов». Связи между ними нет,
и руководителю нечего ответить на вопрос «а что мне даст планшет».

Гипотеза формулируется так:

> Подпись «Готов к выбытию» с планшета ставится **на месте, в момент приёмки работ**.
> Подпись с ПК ставится **позже, из кабинета, по памяти или по бумажке**. Во втором
> случае работу фактически не принимают — и машина возвращается с тем же дефектом.

Если гипотеза верна, доля возвратов среди нарядов, выбытие которых подписано с ПК,
будет **выше**, чем среди подписанных с планшета. Это превращает «% планшета» из
метрики ради метрики в рычаг, у которого есть измеримое следствие.

Если гипотеза неверна — это тоже результат, и он честнее, чем её отсутствие.
Тогда планшет обосновывается скоростью и прослеживаемостью, а не качеством.

## 2. Задача 1. Возвраты × АРМ выбытия

### 2.1 Что показываем

Один блок, две части.

**Таблица «Возвраты по способу подписания выбытия»:**

| Как подписано выбытие | Нарядов в базе | Из них вернулись | Доля возвратов | Медиана до возврата |
|---|---|---|---|---|
| Планшет (обе дирекции) | | | | |
| Смешанно (одна планшет, другая ПК) | | | | |
| ПК (обе дирекции) | | | | |
| Подписала одна дирекция · планшет | | | | |
| Подписала одна дирекция · ПК | | | | |
| **Итого** | | | | |

Пять строк, а не две, потому что у наряда до **четырёх** подписей: две дирекции ×
два статуса. Сводить их в «планшет / ПК» одним махом нельзя — потеряется именно то,
что интересно: наряд, где ДГМ подписал с планшета, а ДЭНТ с ПК.

**Под таблицей — вывод, посчитанный кодом**, в одном из трёх вариантов:

- разрыв значим: «Наряды, выбытие которых подписано с ПК, возвращаются в N раз чаще:
  X % против Y %. Разрыв Z п.п.»;
- разрыва нет: «Способ подписания выбытия на долю возвратов не влияет: X % против Y %,
  разрыв меньше одного процентного пункта»;
- данных мало: «В группе ПЛАНШЕТ всего N нарядов с закрытым окном — для вывода мало».

### 2.2 Определения, без которых блок посчитает ерунду

**База (знаменатель).** Наряд входит, если выполнено всё:

1. внеплановый (`IsPlanned(zn_type) = False`) и характер работы = «Отказ» —
   то же определение, что у главной плитки слайда 6, иначе числа не сойдутся;
2. есть хотя бы одна подпись «Готов к выбытию» с `arm ∈ {ПК, ПЛАНШЕТ}` —
   без неё наряд нечего классифицировать;
3. наряд закрыт (`zn_closed > 0`) — отсчёт окна возврата идёт от закрытия;
4. создан не раньше `REPORT/YTD_START`;
5. **окно возврата успело закрыться** — см. 2.3. Это условие критично.

**Числитель.** Наряды базы, после которых в окне 30 суток случился возврат:
машина вернулась с той же подкатегорией дефекта, повторный наряд — тоже отказ.
Определение возврата берётся ровно то, что уже реализовано в `RetPairs(mode = 2,
winDays = 30)`.

**Классификация строки.** По полям АРМ подписи «Готов к выбытию»:
ДГМ и ДЭНТ. Если обе подписи есть — «обе дирекции», далее по совпадению АРМ.
Если одна — отдельные строки «подписала одна дирекция».

**Медиана до возврата** — медиана интервала «закрытие первого наряда → создание
повторного», сутки.

### 2.3 Ловушка первая: незакрытое окно

**Это самая опасная ошибка в задаче, и без её обхода блок покажет ложь.**

У наряда, закрытого пять дней назад, возврат физически не успел случиться — окно
30 суток не истекло. Такой наряд в знаменателе есть, а в числителе быть не может,
и он занижает долю возвратов.

Само по себе это ещё не катастрофа. Катастрофа в том, что **свежие наряды
распределены между группами неравномерно**: планшет внедряют, и доля подписей с
планшета в последние месяцы выше, чем год назад. Значит в группе ПЛАНШЕТ окажется
больше нарядов с незакрытым окном, её доля возвратов будет искусственно занижена —
и блок «докажет» гипотезу, которая на деле не проверялась.

**Решение:** в базу берутся только наряды, закрытые не позже чем за 30 суток до
конца снимка: `zn_closed <= SnapshotEnd() - RET_WINDOW`.

Число отсечённых нарядов выводится под таблицей отдельной строкой: «Исключено N
нарядов, закрытых в последние 30 суток — окно возврата у них не истекло». Читатель
должен видеть, что отсечение было, иначе он не поймёт, почему числа не сходятся
с плитками слайда 6.

### 2.4 Ловушка вторая: разрыв может быть не про планшет

Доля возвратов зависит не только от способа подписи. Она зависит от того, **что
именно чинили** и **где**. Если планшетами пользуется одна ремзона, а она же берёт
на себя простые дефекты, то её низкая доля возвратов — заслуга простых дефектов,
а не планшета.

Отчёт не может это разделить: у нас наблюдение, а не эксперимент. Но он обязан
не выдавать корреляцию за причину.

**Решение — контрольный разрез.** Под основной таблицей — вторая, компактная:
доля возвратов по способу подписания **внутри каждой из трёх самых частых групп
дефекта**. Если разрыв сохраняется во всех трёх — гипотеза устояла. Если в одной
группе разрыв есть, а в других нет — дело не в планшете, и это видно сразу.

**В пояснении под блоком — прямым текстом:** «Блок показывает связь, а не причину.
Наряды не распределялись по способу подписания случайно: планшетом пользуются
определённые люди в определённых ремзонах, и на долю возвратов влияет ещё и то,
что именно чинили. Контрольный разрез ниже проверяет, держится ли разрыв внутри
одной группы дефекта».

### 2.5 Чего сейчас нет в коде

Задача не сводится к новой функции — нужны два изменения в снимке.

| Что | Где сейчас | Что нужно |
|---|---|---|
| АРМ подписи «Готов к выбытию» | `modContentDisc`, поля `E_LG` / `E_LD`. В `modContentZone` хранятся только **даты** подписей (`Z_LEVG`, `Z_LEVD`), АРМ там нет | Добавить в `mZn` два поля: `Z_ARMLEVG`, `Z_ARMLEVD`. Заполняются в том же проходе `EnsureZn`, где уже читается `arm` |
| Признак «наряд породил возврат» | `mRetOrd` помечает **второй** наряд пары — тот, что приехал повторно | Нужен обратный словарь `mRetSrc`: **первый** наряд пары, тот самый, после которого вернулись. Заполняется там же, в `RetPairs`, соседней строкой |

Почему нельзя просто посчитать это в `modContentDisc`, где АРМ уже есть: там нет
классификатора дефектов (`Z_KIND`, `Z_NODE`) и нет пар возвратов. Дешевле протащить
два строковых поля в `mZn`, чем переносить весь расчёт возвратов в другой модуль.

### 2.6 Размещение

Слайд 6 «Дефекты, хроники и повторы», сразу после плиток возвратов
(`{{BLOCK_RET_KPI}}`). Там уже задано определение возврата, и блок читается как
его продолжение: «сколько возвратов» → «а от чего они зависят».

Новый плейсхолдер: `{{BLOCK_RET_BY_ARM}}`.

Дублировать блок на слайды 2–3 не нужно: он не про дирекцию, а про способ подписи.
На слайдах дирекций достаточно ссылки в пояснении `{{BLOCK_ACCLEV_*}}`.

## 3. Задача 2. Дельта по годам

### 3.1 Что показываем

Сейчас год к году сравниваются только отказы помесячно
(`{{BLOCK_FAIL_MONTH_YOY}}`, сделано 17.09). Руководству нужен сводный ответ
«стало лучше или хуже» по всем ключевым числам сразу.

**Таблица «Год к году · сопоставимые периоды»:**

| Показатель | янв–{месяц} {прошлый год} | янв–{месяц} {текущий год} | Δ | Δ % |
|---|---|---|---|---|
| Заказ-нарядов создано | | | | |
| Из них внеплановых | | | | |
| Из них отказов | | | | |
| Заездов техники | | | | |
| Машин побывало в ремонте | | | | |
| Возвратов (30 суток) | | | | |
| Доля возвратов, % | | | | |
| Медиана срока наряда | | | | |
| Материалы, руб. | | | | |
| % подписей с планшета | | | | |

Последняя строка — только если в прошлом году подписи вообще были: планшет могли
внедрить позже.

### 3.2 Сопоставимость периодов

**Правило:** сравниваются январь — месяц, которым обрывается снимок, обоих лет.
Не полный прошлый год против неполного текущего. Это то же правило, что уже
применено в `BuildFailMonthYoY`, и оно должно быть общим для всех блоков «год к году».

В подписи периода — конкретные даты обоих отрезков, а не слова.

### 3.3 Если прошлого года в выгрузке нет

Блок определяет это сам: если в прошлом году ни одного наряда — рисуется одна
колонка текущего года и строка: «Данных за {год} в выгрузке нет, сравнивать не с чем.
Появятся — блок станет сравнительным сам, править код не нужно».

Колонка нулей не рисуется: она читается как «в прошлом году ничего не было», а это
неправда — это отсутствие данных, а не отсутствие работы. Разница принципиальная.

### 3.4 Окраска дельты

Не все показатели «чем больше, тем лучше». Для каждой строки направление задаётся явно:

| Рост — это хорошо | Рост — это плохо |
|---|---|
| % подписей с планшета | возвраты и их доля |
| машин побывало в ремонте (охват) | медиана срока наряда |
| | отказы |

Нейтральные (наряды, заезды, материалы) не красятся вовсе: рост числа нарядов сам
по себе не хорош и не плох, он зависит от объёма работы.

### 3.5 Размещение

Слайд 1 «Обзор недели», сразу после плиток KPI. Это первое, что видит руководство,
и первое, о чём спрашивает.

Новый плейсхолдер: `{{BLOCK_YOY_SUMMARY}}`.

## 5. Чего этот отчёт НЕ докажет

Пишу отдельным разделом, потому что об это спотыкаются первым делом.

1. **Причинность.** См. 2.4. Наряды не распределялись по способу подписи случайно.
   Блок показывает связь и проверяет её устойчивость, не более.
2. **Что виноват конкретный человек.** Отчёт не оценивает людей — это записано в
   промпте ИИ и должно остаться в пояснении блока.
3. **Динамику разрыва.** Первая версия даёт срез за год. Разрыв по неделям потребует
   на порядок больше данных в каждой ячейке — предлагаю не делать, пока не увидим
   объёмы в годовом срезе.
4. **Что было бы, если бы все перешли на планшет.** Это прогноз, а отчёту запрещено
   прогнозировать.

Реализация занимает один заход. **Но делать её до прогона предыдущих правок в Excel
я не советую**: в ветке уже девять коммитов кода, который ни разу не компилировался,
и если там есть ошибка, новые сто пятьдесят строк только усложнят её поиск.

Разумный порядок: сначала `compile_check` и `DebugGenerateOffline` на том, что есть,
затем эта постановка.
