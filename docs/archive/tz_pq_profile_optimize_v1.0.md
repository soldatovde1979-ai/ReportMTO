# ТЗ разработчику (агент-исполнитель): профилирование конвейера Power Query и устранение медленной пакетной загрузки

> Версия ТЗ: v1.0 от 13.09.2026. Утверждено владельцем.
> Основание: [`tz_developer_logging_and_release_v1.0.md`](tz_developer_logging_and_release_v1.0.md) (задачи 1–10 выполнены,
> регламент п.10 сработал) и [`analysis_loadpackage_hang_v1.0.md`](analysis_loadpackage_hang_v1.0.md)
> (эскалация: загрузка 217 768 записей висит > 1 часа внутри `Refresh`, лог остановился на вехе «До Refresh»).
> Правила исполнения: только точечные правки; комментарии и алгоритмы не удалять; ничего не переписывать целиком
> без необходимости; перед правкой читать целевой участок файла; после правок — блок отчёта
> «Внесенные изменения / Намеренно не тронуто / Потенциальные риски».

## Цель

Найти точное место стоимости внутри конвейера Power Query (измерением, не гипотезами), устранить подтверждённые
замерами причины медленной загрузки, добавить прогноз ожидания перед `Refresh` (закрыть жалобу владельца
«логов нет») и закрыть цикл build/e2e/релиз/контрольная загрузка.

## Общий порядок выполнения

0 → A (профилирование) → решение владельца по результатам A → B (оптимизации только по замерам) →
C (прогноз ожидания) → D (build/e2e/релиз/контрольная загрузка).

Правки боевого конвейера до выполнения задачи A **запрещены**.

## Задача A. Профилирование конвейера (точное «где», без гадания)

A.1. Создать диагностические запросы `src\powerquery\qProf1_Source.pq` … `qProf7_Retention.pq`.
Каждый запрос — **копия конвейера** [`Query-ImportJSON.pq`](../src/powerquery/Query-ImportJSON.pq:53),
оборванная на своём шаге; возвращает таблицу `1×1` с числом строк этого шага (например `#table({"Rows"}, {{Table.RowCount(Expanded)}})`).
Тот же `prmSourcePath`, тот же режим папки. Список:

| Запрос | Обрывается на шаге | Что измеряет |
|---|---|---|
| `qProf1_Source` | `Source` | чтение и парсинг JSON всех файлов папки |
| `qProf2_Expanded` | `Expanded` | разворачивание записей в таблицу |
| `qProf3_Normalized` | `Normalized` | `fnNormalizeFields` |
| `qProf4_Key` | `WithKey` | `fnComputeKey` |
| `qProf5_Dedup` | `Deduped` | `fnDedupByKey` (сортировка + `Table.Distinct`) |
| `qProf6_Groups` | `WithGroups` | `fnComputeGroupMetrics` |
| `qProf7_Retention` | `Retained` | ретеншн (`ToDT`/`RowAnchor`/`Cutoff`) |

A.2. Инструмент прогона — временный `tools\_tmp_profile_pq.ps1` (по образцу
[`tools\_tmp_load_package.ps1`](../tools/_tmp_load_package.ps1:1)): открывает build-книгу, ставит
`prmSourcePath` на нужную папку. **Внимание:** запросы `qProf*` должны быть выведены на временный лист Excel (в виде `QueryTable`), иначе `Refresh` может кэшироваться или не выполняться движком Power Query. Скрипт принудительно обновляет каждый `qProfN` (через ListObject.QueryTable.Refresh с `BackgroundQuery := False`),
меряет `Timer` снаружи M и печатает/пишет вехи вида `ЭТАП qProf3_Normalized: 217768 строк, 412.5 c`.
Стоимость шага = разница соседних замеров.

A.3. Прогон в два этапа (согласовано с анализом, §5):
- сначала на **одном** файле `sppr_tablet_20260910_211120_4976rec.json` (4976 записей) — для этого временная
  папка (например `data\_prof1\`) с копией этого файла и `prmSourcePath` на неё;
- затем на **двух** файлах (4976 + 17552, по возрастанию даты) — временная папка `data\_prof2\`;
- экстраполяция на 5 файлов / 217 768 записей. Нелинейность допустима — задача найти доминанту, а не прогноз.

A.4. Результат оформить вехами в `ReportMTO.log` build-книги и таблицей «этап | строк | секунды | доля»
в [`docs/tasks.md`](../tasks.md:1). Решение владельца по составу оптимизаций (какие пункты B включать)
принимается по этой таблице.

A.5. `qProf*` — диагностические; в установку не идут (как `qDiagImport`). Временные папки и
`_tmp_profile_pq.ps1` удалить после завершения всей работы.

## Задача B. Устранение причин (только по результатам задачи A, в порядке убывания стоимости)

Каждую правку делать отдельным шагом с контрольным замером; правку, не давшую подтверждённого выигрыша,
откатывать. Семантика результата должна остаться идентичной (сверка «N из M», тесты ниже).

B.1. **Ретеншн без `try` в режиме папки.**
[`Query-ImportJSON.pq`](../src/powerquery/Query-ImportJSON.pq:146): в режиме папки с пустой `tbDATA` все даты
уже типизированы в `fnNormalizeFields` — заменить терпимую конвертацию `ToDT`/`RowAnchor` на прямое сравнение
`datetime` (с учётом `null`: строка без обеих дат сохраняется, правило не меняется). Ветку с `try` оставить
только для режима одного файла (там из `qExistingData` приходят `any`/`text` — см. комментарий в коде).
Проверка: [`tools\check_retention.ps1`](../tools/check_retention.ps1:1) — значения KW0/KW52/KW1 должны совпасть
до и после правки.

B.2. **`fnComputeGroupMetrics` одним проходом.**
[`fnComputeGroupMetrics.pq`](../src/powerquery/fnComputeGroupMetrics.pq:37): сейчас внутри `Table.Group` на каждую
пару `(number, direction)` выполняются два `Table.SelectRows` по подтаблице. Заменить: ДО группировки добавить
колонки-носители (для стартовых строк — `status_date`, иначе `null`; аналогично для конечных), затем агрегировать
`List.Min`/`List.Max` по этим колонкам внутри стандартного агрегата `Table.Group` (чтобы движок потоково сворачивал данные без внутренних `SelectRows`). Вложенные сканирования уходят. Семантика `IsStart`/`IsEnd`/`deltaHours`
не меняется (сравнение нормализованное, «ё»→«е» — сохранить).

B.3. **`fnComputeKey` без построчного `try`.**
[`fnComputeKey.pq`](../src/powerquery/fnComputeKey.pq:67): сейчас `try DateTime.ToText(...)` на каждую строку.
Определить поддержку трёхаргументной формы **один раз** (проба на одном значении с `try`) и передать флаг
в форматирование. Формат ключа и комментарии о миграции — сохранить.

B.4. **Ревизия буферов.**
Оставить: `List.Buffer` в `Source` (нужен) и один `Table.Buffer` перед выгрузкой (`UpsertedBuf`).
Убрать или пересмотреть: `Table.Buffer` в [`fnDedupByKey.pq`](../src/powerquery/fnDedupByKey.pq:38)
(обязательно перепроверить детерминизм `Table.Distinct` — по спецификации M `Table.Distinct` без предварительного `Table.Buffer` **не гарантирует** сохранение порядка; если бизнес-логике критично сохранение первой записи из отсортированных, буфер перед `Distinct` **сохранить**). Также пересмотреть: `Table.Buffer(tbl)` и `Table.Buffer(Lookup)` в `fnComputeGroupMetrics`, `Table.Buffer(WithGroups)`
(`NewData`). Каждое удаление — с контрольным замером времени и сверкой результата.

B.5. **Режим папки не вычисляет `qExistingData`.**
[`Query-ImportJSON.pq`](../src/powerquery/Query-ImportJSON.pq:128): ветку `Upserted` переписать как
`if not IsFolder then <текущая upsert-логика> else NewData` — чтобы в режиме папки `qExistingData` не
материализовался вовсе (сейчас `Table.RowCount(ExistingData)` форсирует его вычисление всегда).
Режим одного файла оставить без изменений.

B.6. **Базовые точки.** До оптимизаций зафиксировать: либо результат текущего прогона (задача 0), либо время
полной загрузки на build-книге по замерам `qProf7`. После оптимизаций — повторить и сравнить.

## Задача C. Индикация живости (закрывает «логов нет»)

C.1. В [`LoadPackage()`](../src/vba/modMain.bas:103) перед `SetSourcePathParameter`/`Refresh`:
- прочитать ключи `Variable` `DATA/LAST_LOAD_SECONDS` и `DATA/LAST_LOAD_ROWS` (результаты последней успешной пакетной загрузки; нет ключей → прогноза нет);
- если прогноз есть — веха `WriteMilestone` «Refresh начат: N записей, ожидание ~M мин» (где M = (LAST_LOAD_SECONDS / LAST_LOAD_ROWS * N) / 60);
  иначе — веха «Refresh начат: N записей, прогноза нет (первый замер)»;
- тот же текст — в `Application.StatusBar`; в конце процедуры и в `ErrHandler` StatusBar гасить (как в `GenerateReport`).

C.2. После успешного завершения (после вехи «Записано N из M») записать фактическое время в ключ `DATA/LAST_LOAD_SECONDS` и количество строк в ключ `DATA/LAST_LOAD_ROWS`
(ключи создаются при первом прогоне; без миграции — пишутся из VBA при отсутствии).

C.3. Запрещено: фоновая запись лога во время синхронного `Refresh` (VBA заблокирован — технически невозможно)
и запись лога из M-кода. «Каждая строка» не требуется — только прогноз до и факт после.

## Критерии приёмки

- До оптимизаций получена таблица «этап | строк | секунды | доля» и назван виновник (подтверждено владельцем).
- Каждая правка задачи B подтверждена замером; неприбыльные правки откатаны.
- «Записано N из M» после оптимизаций совпадает с эталоном (217 768), KW0/KW52/KW1 совпадают, e2e зелёный.
- В `ReportMTO.log` перед `Refresh` видна веха прогноза; после завершения — фактическое время.
- Релиз с `VERIFY_OK` + `COMPILE_OK`; e2e прогонялся ДО релиза; контрольная загрузка выполнена с таймингом.

## Общие ограничения (действуют для всех задач)

- Не менять: схему `tbDATA`, лист `Logs`, лист `Variable` (кроме ключа `DATA/LAST_LOAD_SECONDS`),
  контракт `modLog`, `fnNormalizeFields`, `fnUpsert`, `qKeepWeeks`, `tmp_index.html`, миграции.
- Не менять конвейер до замеров задачи A; комментарии, расчёты и историю решений в `.pq`/`.bas` сохранять.
- Временные файлы — только `tools\_tmp_*`; после завершения удалить.
- Секреты и пароли в логи не писать. После каждого изменения файла — блок отчёта
  «Внесенные изменения / Намеренно не тронуто / Потенциальные риски».
