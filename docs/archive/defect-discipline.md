# Источник данных для трека C (дисциплина регистрации дефекта/ЗН)

Собрано из переписки с Дмитрием 2026-09-05, для проектирования track C
(легитимность регистрации через ПТСД/планшет), пока не постановка —
разговор об архитектуре.

## Подтверждённые факты

1. `eamОбнаруженныйДефект` (ОД) и `eamЗаказНаряды` (ЗН) — два разных
   документа 1С:ERP EAM. Track A/B в текущей выгрузке `sppr_tablet_*.json`
   строится по `eamЗаказНаряды` (поле `ready_for` = "Готов к приёмке" /
   "Готов к выбытию", берётся из `РегистрСведений.eamСтатусыОбъектов`).
2. Последовательность статусов track C, подтверждено по коду и
   пользователем (по объекту, к которому привязана запись регистра
   `eamСтатусыОбъектов.Объект`):
   - **ОД (дефект)**: "Создан" > "Сформирована заявка" — оба статуса
     самого дефекта, идут последовательно на одном объекте.
   - В момент перевода ОД в "Сформирована заявка" **ЗН создаётся
     автоматически, но не проводится**.
   - **ЗН (заказ-наряд)**: "Заявка открыта" — статус самого ЗН,
     появляется только после того как ЗН **проведён**.
   - Итоговая цепочка: `ОД.Создан > ОД.Сформирована заявка > (ЗН создан,
     не проведён) > ЗН.Заявка открыта (после проведения)`.
   - Это тот же регистр сведений `eamСтатусыОбъектов`, что и
     "Готов к приёмке"/"Готов к выбытию" в текущей выгрузке — источник
     общий, но текущая `СформироватьJSONПланшет` эти статусы не читает:
     JSON-схема (`data.md`) ограничивает `ready_for` enum двумя
     значениями, `arm` enum — `["ПК","ПЛАНШЕТ"]`, без ПТСД.
3. Легитимность в примере пользователя завязана не на поле `arm` (как в
   треке A), а на **`шхТипРМ`** — тип рабочего места. Снимается
   **отдельно для ОД и для ЗН** через `СрезПервых` того же регистра:
   `ПервыйСтатусОД.шхТипРМ` (тип РМ дефекта) и `ПервыйСтатусЗН.шхТипРМ`
   (тип РМ заказ-наряда). Состав значений поля (есть ли литерал "ПТСД")
   не проверен.
4. Список исключений по виду дефекта (`шхКлассификаторДефекта` /
   `defekt_type`) может меняться со временем — при проектировании
   учитывать как отдельный справочник (по аналогии с `dictZone`/
   `dictDefect`), не хардкодить в коде. В статистику такие исключения
   попадают как «хорошие» (легитимные) записи.

## Открытые вопросы (не проверено, спросить)

- Состав значений `шхТипРМ` — какие литералы там встречаются (ПТСД, ПК,
  Планшет и т.п.) и точно ли легитимность дефекта = "ПТСД", легитимность
  ЗН = "Планшет" (кроме исключений по `defekt_type`).
- Первый присланный блок кода (`СформироватьJSONНаСервере` /
  "ВЫГРУЗКА 1: ИДЕИ") оперирует справочниками `Идеи`, `Карточка`,
  `СоответствиеСценариевТребованиям` — это не домен МТО/eam, похоже на
  код из другой подсистемы (трекер требований/идей проекта). Приведён в
  файле как есть, без интерпретации — возможно прислан по ошибке или как
  образец стиля JSON-выгрузки, не домен ОД/ЗН.
