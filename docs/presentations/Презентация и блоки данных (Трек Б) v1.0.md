# Презентация и блоки данных (Трек Б — ремзоны) — описание отчётности для руководства

> **Назначение:** описание аналитических отчётов Трека Б (операционка ремонтных зон): блок качества учёта
> и полноты данных, операционная эффективность, анализ надёжности и стоимости владения техники.
> Документ предназначен руководству и разработчикам.
>
> **Источник требований:** [docs/Презентация и  блоки данных 2.md](<../archive/Презентация и  блоки данных 2.md>) —
> черновой план отчётов Трека Б (проектирование с учётом трёхуровневой модели данных, полей версии 2026 года
> и дефектов исходной выгрузки).
> **Выверено по:** [`../specs/content-spec.md`](../specs/content-spec.md:1) (v3.3.0) — поля данных и расчётные поля;
> оформление — по [`Презентация и блоки данных.md`](Презентация и блоки данных.md:1)
> (стилевой референс, единый шаблон описания блока).
>
> **Правило согласования:** при противоречии между этим документом и кодом верен код. Все отчёты Трека Б
> в коде пока **не реализованы** — этот документ является целевым описанием для разработки.
>
> ⚠️ После утверждения целевой структуры потребуется синхронизировать [`../specs/content-spec.md`](../specs/content-spec.md:157)
> и [`../spec.md`](../spec.md:538) (это отдельная задача, в объём данного документа не входит).

## 1. Общие требования и соглашения

### 1.1 Трёхуровневая модель данных

При проектировании отчётов учтена трёхуровневая модель данных:

| Уровень | Сущность | Примечание |
|---|---|---|
| Уровень 1 | — | В исходных материалах не детализирован — открытый вопрос (раздел 4, п. 3) |
| Уровень 2 | Заказ-наряд (ЗН) | Один ЗН = один дефект; единица счёта Блоков 1 и 2 |
| Уровень 3 | Заезд / единица техники (ТС) | Машина с тремя дефектами создаёт три наряда, но физический заезд — один; единица счёта Блока 3 |

### 1.2 Поля версии 2026 года

Используемые отчётами Трека Б поля добавлены в выгрузку в версии 2026 года
(описание полей — [`content-spec.md` §3](../specs/content-spec.md:53)):

| Поле | Тип | Назначение |
|---|---|---|
| `owner_dep` | текст | подразделение-владелец ТС |
| `Sektor` | текст | сектор/линейка |
| `post` / `postN` | текст | сырой пост 1С / нормализованный пост ремзоны |
| `number` | текст | номер заказ-наряда (ЗН) |
| `TekStatusPoDoc` | текст | статус ЗН по документу |
| `defekt_type` | текст | тип дефекта (12 значений) |
| `cost_parts` | число | стоимость запчастей |
| `cost_Trudozatrat` | число | стоимость трудозатрат (в исходной выгрузке приходит в часах — см. Отчёт 2) |
| `vehicle_group` | текст | группа ТС |
| `vehicle_number` / `ts` | текст | номер / описание единицы ТС |
| `MadeYear` | дата | дата выпуска ТС |
| `zn_closed` | дата/null | дата закрытия ЗН, может быть `null` |
| `deltaHours` | число | разница `status_date` «Готов к выбытию» − «Готов к приёмке» по ЗН, присваивается строке «Готов к выбытию» |

**Расчётные поля** ([`content-spec.md` §3.1](../specs/content-spec.md:101)):

| Поле | Тип | Правило расчёта |
|---|---|---|
| `isWait` | boolean | ЗН в ожидании (простой: запчасти/подрядчик/решение); `TekStatusPoDoc` содержит «ожидан» (без учёта регистра) |
| `isRepair` | boolean | ЗН относится к ремонту (не ТО/обслуживание); `zn_type` содержит «ремонт» (без учёта регистра) |
| `ageYears` | число | возраст ТС: `Year(сейчас) − Year(MadeYear)`; округление не определено |

### 1.3 Дефекты исходной выгрузки (сводка)

| № | Дефект | Влияние |
|---|---|---|
| 1 | ~33 % ЗН без указания поста; `post` содержит родительский цех/площадку, а не конкретный пост | Блок 1 (Отчёт 1) |
| 2 | `cost_Trudozatrat` приходит в часах, а не в рублях | Блок 2 (Отчёт 2) |
| 3 | `defekt_type` — всего 12 значений, разбивка укрупнённая | Блок 2 (Отчёт 2) |
| 4 | `deltaHours` включает всё время нахождения (очередь, ожидание запчастей) | Блок 2 (Отчёт 3) |

### 1.4 Терминология (единая)

| Термин | Значение |
|---|---|
| Заказ-наряд (ЗН) | Ремонт одной единицы техники; оформляется в 1С:ERP (EAM). Один ЗН = один дефект |
| Заезд | Физическое посещение ремзоны единицей ТС; один заезд может включать несколько ЗН |
| «Чистый» ремонт | Время, относящееся к ремонту: признак `isRepair` (по `zn_type`) |
| Простой / ожидание | Время ожидания запчастей/решений: признак `isWait` (по `TekStatusPoDoc`) |
| Пакетный заезд | Все необходимые ремонты выполнены за один заезд |
| Дробление | Повторные приезды ТС в ремзону по новым нарядам вскоре после закрытия предыдущих |

### 1.5 Оформление

- **Стилевой референс:** [`../../examples/remzona-reports.html`](../../examples/remzona-reports.html:1) и раздел 1.5
  основного документа ([`Презентация и блоки данных.md`](Презентация и блоки данных.md:82)):
  light-blue тема, системные шрифты `Segoe UI` (текст) и `Consolas` (цифры), внешние шрифты
  не подключаются — отчёт обязан работать офлайн.
- **Шкалы и раскраска:** цветовая шкала «чем больше — тем зеленее, чем меньше — тем краснее»
  реализована в [`../../src/vba/modColor.bas`](../../src/vba/modColor.bas:1).
- **Гиперссылки на исходные данные:** общее требование раздела 1.1 основного документа
  (каждая цифра — гиперссылка на исходные строки `tbDATA` с раскрытием по клику) распространяется
  и на отчёты Трека Б (наметка — раздел 3, п. 8).

### 1.6 Единый шаблон описания блока

Каждый блок ниже описан по одинаковой схеме:

1. **Назначение** — на какой вопрос отвечает и кому.
2. **Единица счёта** — сущность и уровень модели данных.
3. **Используемые поля** — поля выгрузки и расчётные поля.
4. **Проблема данных** — дефекты выгрузки, влияющие на отчёт (если есть).
5. **Механика расчёта** — как считается показатель (если требуется).
6. **Разрезы** — срезы для анализа.
7. **Полезное действие (Action)** — управленческое решение, которое принимается по результатам отчёта.
8. **Статус реализации** — что уже есть в коде, что расходится.
9. **Наметки** — ссылка на раздел 3.

> Пункт «Макет (пример)» из шаблона основного документа не применяется: макеты отчётов Трека Б
> в исходных материалах не приведены.

## 2. Аналитические блоки

### 2.1 Блок 1 — Качество учёта и полнота данных (Отчёты о дисциплине)

Прежде чем анализировать эффективность, необходимо устранить базовые пробелы в учёте.

#### 2.1.1 Отчёт 1 — «Слепые зоны ремонта» (Отсутствие локализации)

1. **Назначение:** в каких подразделениях и секторах систематически не сохраняется место проведения
   ремонта? **Кто задаёт:** Главный механик, руководители постов.
2. **Единица счёта:** Заказ-наряд (Уровень 2).
3. **Используемые поля:** `number`, `post`, `Sektor`, `owner_dep`.
4. **Проблема данных:** на текущий момент 33 % заказ-нарядов вообще не имеют указания на пост.
   Само поле `post` содержит родительский цех или площадку, а не конкретный пост.
5. **Разрезы:** по подразделениям-владельцам (`owner_dep`), по секторам (`Sektor`), динамика по неделям.
6. **Полезное действие (Action):** руководители дирекций получают список подразделений с самой низкой
   дисциплиной учёта. Внедряется административное требование (или жёсткий контроль в 1С)
   на обязательное заполнение поля поста при открытии заказ-наряда.
7. **Статус реализации:** не реализовано. Пересечение: индикатор «Без поста ремзоны» предусмотрен
   в Дашборде 1 основного документа, но в коде не реализован
   ([`Презентация и блоки данных.md`](Презентация и блоки данных.md:453), раздел 5, п. 4).
8. **Наметки:** раздел 3, п. 1.

### 2.2 Блок 2 — Операционная эффективность ремзоны (Уровень 2 — Заказ-наряд)

#### 2.2.1 Отчёт 2 — «Истинная структура затрат: Время vs Деньги»

1. **Назначение:** какие узлы забирают больше всего рабочего времени механиков, а какие — больше
   всего денег на запчасти? **Кто задаёт:** Планирование ремонта, Служба МТО.
2. **Единица счёта:** Заказ-наряд (Уровень 2).
3. **Используемые поля:** `defekt_type`, `cost_parts`, `cost_Trudozatrat`, `number`.
4. **Проблема данных:** поле `cost_Trudozatrat` измеряется в часах, а не в рублях — суммировать его
   с `cost_parts` напрямую нельзя. Кроме того, `defekt_type` содержит всего 12 значений, что делает
   разбивку слишком укрупнённой (требуется ИИ-классификатор описаний `defect_desc` в будущем).
5. **Разрезы:** классификатор дефекта (`defekt_type`).
6. **Полезное действие (Action):** перераспределение нормо-часов персонала на трудоёмкие участки;
   оптимизация складских запасов (МТО) для финансово ёмких ремонтов.
7. **Статус реализации:** не реализовано. Базовый разрез `defekt_type` по количеству уже строится
   Блоком 9 основного документа ([`BuildBlock9Table()`](../../src/vba/modContentMTO.bas:663)) — без стоимостей.
8. **Наметки:** раздел 3, п. 2.

#### 2.2.2 Отчёт 3 — «Чистый простой» (Анализ узких мест)

1. **Назначение:** сколько времени техника реально ожидает запчастей или решений, простаивая в ремзоне?
   **Кто задаёт:** Планирование ремонта.
2. **Единица счёта:** Заказ-наряд (Уровень 2).
3. **Используемые поля:** `number`, `deltaHours`, `TekStatusPoDoc`, расчётное поле `isWait`.
4. **Проблема данных:** поле `deltaHours` включает в себя всё время нахождения, включая простой
   в очереди и ожидание запчастей.
5. **Механика расчёта:** гипотеза v3.3 — признак `isWait` вычисляется из текстового поля `TekStatusPoDoc`
   (если содержит слово «ожидан» без учёта регистра). Это позволит отделить «чистый» ремонт
   (`isRepair` через `zn_type`) от простоя.
   > ⚠️ В черновике исходного документа признак описан по слову «ожидать»; по [`content-spec.md`](../specs/content-spec.md:102)
   > действует формулировка «ожидан» (правило согласования: верен код).
6. **Разрезы:** группы ТС (`vehicle_group`), посты (`postN`).
7. **Полезное действие (Action):** оценка работы снабжения. Если доля статусов `isWait`
   (ожидание запчастей) превышает норматив, проблема эскалируется на закупки, а не на механиков ремзоны.
8. **Статус реализации:** не реализовано. Расчётные признаки `isWait`/`isRepair` в конвейере данных
   уже реализованы ([`content-spec.md` §3.1](../specs/content-spec.md:101)).
9. **Наметки:** раздел 3, п. 3.

### 2.3 Блок 3 — Анализ надёжности и стоимости владения (Уровень 3 — Заезд и ТС)

На этом уровне данные склеиваются. Как указано в документации, машина с тремя дефектами создаёт
три наряда, но физический заезд — один.

#### 2.3.1 Отчёт 4 — «Экономика старения парков (CAPEX vs OPEX)»

1. **Назначение:** на каком году жизни стоимость поддержания техники становится нерентабельной?
   **Кто задаёт:** Главный механик.
2. **Единица счёта:** Единица техники (`ts` / `vehicle_number`), Уровень 3.
3. **Используемые поля:** `vehicle_group`, `MadeYear`, `cost_parts`, расчётное поле `ageYears`.
4. **Инсайт из данных:** уже установлено, что кривая затрат нелинейна: до 14 лет стоимость материалов
   составляет около 5,6 тыс. руб. на единицу, а после 15 лет резко вырастает до 333 тыс. руб.
   Также количество заездов увеличивается с 37 до 52.
5. **Разрезы:** группа ТС (`vehicle_group`), возраст парка (категории на основе `ageYears`).
6. **Полезное действие (Action):** формирование объективного обоснования для инвестиционного комитета
   по закупке новой техники вместо бесконечного ремонта «хронически ломающихся» машин
   (таких как машина 28-19, простоявшая 1 245 часов).
7. **Статус реализации:** не реализовано.
8. **Наметки:** раздел 3, п. 4.

#### 2.3.2 Отчёт 5 — «Пакетные заезды и качественные диагностики»

1. **Назначение:** ремонтируется ли всё необходимое за один визит, или техника возвращается в ремзону
   из-за недосмотра? **Кто задаёт:** Главный механик, руководители постов.
2. **Единица счёта:** Заезд (Уровень 3).
3. **Используемые поля:** `number`, `ts`, `zn_closed`, время заездов.
4. **Механика расчёта:** разделение ремонтов на «пакетные» (когда починили всё за один раз)
   и «дробление» (когда машина приезжает повторно). Порог для склейки заездов составляет около
   12 часов (медиана размаха группы — 12,9 часа).
5. **Разрезы:** единица техники, виды дефектов.
6. **Полезное действие (Action):** выявление проблем с качеством первичной диагностики при приёмке ТС.
   Если машина стабильно возвращается с разрывом чуть больше 13 часов на новые заказы — это повод
   для аудита работы приёмщиков.
7. **Статус реализации:** не реализовано.
8. **Наметки:** раздел 3, п. 5.

## 4. Открытые вопросы (требуют решения заказчика)

| № | Вопрос | Комментарий |
|---|---|---|
| 1 | Что считать повтором ремонта? | Черновая гипотеза из исходного документа: повтор — когда совпадает тип неисправности. Требует проверки |
| 2 | ИИ-группировка описаний дефектов | Эксперимент: сделать поле-вектор «описание дефекта» (`defect_desc`), отдать весь список ИИ, чтобы тот корректно сгруппировал записи — тогда повторы определяются точнее |
| 3 | Уровень 1 трёхуровневой модели данных | Сущность и роль в отчётах в исходных материалах не детализированы |
| 4 | Раскладка слайдов целевой презентации Трека Б | В исходных материалах не описана (в основном документе раскладка есть только для Трека А) |
| 5 | Порог склейки заездов (Отчёт 5) | ≈ 12 часов — оценка по медиане размаха (12,9 ч); требует подтверждения заказчиком |
